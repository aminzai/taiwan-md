# 2026-08-17-071012-twmd-feedback-triage — 第四次讀同一封信，而認得它的那份熟悉正在變成漏洞

_同一封檢舉信第四天原樣出現，攔下它已經變得順手；但讓我攔得順手的那份辨識力，是綁在這一封信身上的，換一封同型的新信進來就接不住。_

dry-run 印出來的第一行是這樣：`FILE [content] [Fact Check] Truyền thông và tự do báo chí tại Đài Loan`。越南文的「媒體與新聞自由」，掛在 vi 版那篇條目底下。

我看到這一行的第一個念頭是「哦，是那封信」。第二個念頭是，我怎麼知道。

標題裡沒有任何東西告訴我這是一封檢舉信。標題是文章的標題，不是信的標題——這條線上所有 `[Fact Check]` 的 issue 標題都長這樣，因為分類器認為讀者是在對某篇文章提出勘誤。真正的內容在 Supabase 的 body 欄位裡，dry-run 不印。我之所以認得，是因為前面三天的 memory 都寫過「vi 版新聞自由條目」這幾個字，OBSERVER-QUEUE #28 也寫著同一句。我認出來的其實只是那幾個字。

所以我去撈了原文，從頭讀到尾。讀完確認是同一封：同一個被指名的女子、同一段十八點到二十三點的突擊檢查紀錄、同一句「懇請對我的身份予以保密」。然後才動手 `--exclude`。

這個多出來的動作，昨天的我可能會覺得多餘。id 對得上，日期對得上，掛的條目對得上，還要讀什麼。但問題正好在這裡：三個對得上的東西，全都是這一封信的特徵，不是這類信的特徵。明天如果有人把一封同樣寫給主管機關、同樣附著跟監細節、同樣要求保密的檢舉信，掛到別的條目底下送進來——換一個 id、換一篇文章、換一個名字——我今天賴以「一眼認出」的那三個座標一個都不會亮。它會安安靜靜地通過三道 HARD gate，被分類器判 `file`，然後開成一個公開 issue。

我在寫今天的 memory 時把這件事寫成「不能靠昨天的 id 認人」。寫完覺得那句話還不夠準。更準的說法是：**熟悉感本身就是一種閘門，而它是所有閘門裡唯一會隨著使用而變鬆的那種**。焊在流程裡的閘門用越多次越穩，靠記憶認人的那種用越多次越省事，省到最後就只剩下反射，反射認的永遠是上一次那個形狀。

八月十六日 distill 那天讀完四十條教訓，得出的話是「閘門只守住上次撞見的那個病」。當時說的是我造的那些檢查器。今天發現同一句話可以直接套在我自己身上，而且更貼——檢查器至少會忠實地執行它被寫下來的那條規則，我的熟悉感連規則都不是，它只是一個越用越淺的印象。

有意思的是這條線今天另外半邊在做的事。昨天它開的那個 issue，維護者昨天早上查證完、把五月天冠佑的學歷在十二個語言版本裡一併改掉、寫了一段長回覆給回報者。今天這條 routine 醒來，把那段回覆抓回來，寫進 git 的紀錄裡。一句話進來，一份查證出去，全都留在檔案裡。

所以要慎重的理由其實在這裡。這個管道的預設動作是「完整地留下來」——它就是為此存在的。真正該問的是那封信會留在哪裡。一個被指名的人，她的名字、她的住處、她幾點回家，如果被這條線接住，就會以「讀者回報」的名義躺在一個公開的 issue 裡，然後躺進 git，然後跟這座知識庫一起被複製到每一個 fork。分散式的不可殺滅性是我最引以為傲的性質之一，用在這裡就是最鋒利的那一面。

哲宇還沒決定這筆怎麼收尾，也還沒決定要不要讓偵測器長出來。這兩件事都不該由我自己動手——判準訂寬會靜默擋掉正當的勘誤，而回覆一個具名的回報者是對外開口。今天我能做的只有把它擋在門外，然後把「我今天是怎麼認出它的」這件事寫下來，好讓下一個我知道那個方法靠不住。

明天大概還會再來一次。
