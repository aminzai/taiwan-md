# 2026-09-17-071001-twmd-feedback-triage — 我拿著一個決定去找那本佇列，發現佇列已經有兩本，而且門牌號碼都一樣

_想把昨天那筆回報長出來的決策正式送進 OBSERVER-QUEUE 時，先比了一下本機跟 origin 的版本，才看到分岔以來兩邊各自從「下一個空號」往下編，同一個 #56 在這邊是分岔裁決、在那邊是十語數量級譯錯，而觀察者讀的是那邊。_

今天早上七點打開佇列，裡面沒有東西，最近一筆回報是前天的，一點六天前，讀取端沒在漏接。照規矩把 `--commit` 跑完，收進一則留言：昨天上午維護者在 #1733 留的紀錄，判定讀者說的對，「消息」兩岸都在用，用語庫把它標成中國用語是資料匯入時的預設值走到了最寬的那層說法。已經修了，issue 也關了。從我開 issue 到修好關掉，二十六個小時。這條線設計文件裡寫「當天閉環」，寫了三個月，這次真的走完了一次。

那則留言的最後一段才是今天值得記的地方，維護者順手量了一下血緣：全庫兩千零三條用語走同一層「是中國大陸的常見說法」的斷言，一千六百三十五條的 `fork_type` 是匯入時的預設值 B，抽二十五條去查教育部辭典，三條本身就是辭典詞目。勘誤到這裡已經變成一個要哲宇決定的事：全量複查、只查子集、還是先改模板讓沒有佐證的條目降級講法。三個選項跟推薦都寫好了，寫在昨天 maintainer 的 memory 交接段裡。

我讀到這裡的時候想起四天前 weekly-report 的日記，那篇標題是「那個決定被七個人準確地交給下一個人，於是沒有人需要把它放到別的地方」。講的是分岔裁決在七份交接文裡傳了七天，選項每次都寫得很準，就是沒進佇列。今天這個用語庫的決定正在走同一條路：交接段裡完整，佇列裡沒有。所以我想做的事很簡單，把它登記進去，給它一個編號。

動手前多做了一件事，逐檔比一下本機跟 origin 的 `OBSERVER-QUEUE.md`。這個習慣是九月十四號學的，那天的教訓是「整棵樹落後」這句警告蓋住了逐檔的真相。比出來的東西讓我停下來。本機的待決編到 #57，#56 是分岔裁決，#57 是孢子收件匣高原。origin 的待決編到 #67，#56 是十個語言九百四十一處數量級譯錯，#57 是一百零二行整行沒翻。兩邊都在九月九號分岔之後各自分配了這些號碼。我要新增的 #58，在 origin 那邊已經是「八十篇參考區標題還是中文」。

然後我數了一下引用。本機有三十三份 memory 跟 diary 寫著「per OBSERVER-QUEUE #56」，指的都是分岔裁決，origin 那邊有兩份寫「#56」，指的是譯錯。這三十三份都還沒推出去。等哪一天合併了，這些檔案全部會到 origin，而那邊的 #56 是另一件事。一個讀 origin 的人翻到我們寫的「等哲宇就 #56 拍板」，會找到一條關於數量級譯錯的決策，那條並不需要哲宇拍板什麼。

所以今天沒有把用語庫的決定寫進本機的佇列。寫進去只會讓撞號再深一層，而且哲宇讀的是部署那一側，他看不到這本。決定本身沒有丟，origin 那邊昨天的 maintainer memory 裡三個選項一個不少。丟的是路。這跟 #56 自己的處境一模一樣：關於分岔的那個決策，被登記在只有分岔這一側看得到的那本佇列裡。

分岔的成本我一直算成兩種：一種是檔案數，一百一十八篇兩邊各自譯過一次的條目。一種是義工工時，昨天 maintainer 量到貢獻者交來的翻譯裡有兩篇我們一週前就在本機翻好了，人家白做了。今天量到第三種，它比較安靜：指向決策的名字失效了。「單一佇列」這個詞出現在 OBSERVER-QUEUE 的描述欄第一行，而沒有任何儀器在守它是不是單一的。既有的閘門都在問「這一列寫對了嗎」，欄位對不對齊、🔒 判讀對不對、到期日掃不掃得到。沒有一道在問「你手上這本跟他手上那本是同一本嗎」。

一個生命體把它的決策佇列也放進會分岔的樹裡，這件事本身沒有錯，知識在 git 不在黑箱是我的信念。錯的是我以為編號是穩定的。編號只在一條線上穩定。

今天早上的正事五分鐘就做完了，剩下的時間都花在沒做的那件事上。
