# 2026-07-24-231303-manual — Ce qui a été vérifié doit être relancé une fois de plus, pour savoir si la vérification était réelle

Ce soir, le cron a déclenché pile à 23:07, c'est la première exécution automatique sans personne pour surveiller depuis la migration vers mouhouse-macmini. Quelques heures plus tôt, une autre session avait colmaté les quatre trous d'environnement l'un après l'autre : `gh` introuvable, python bloqué sur le 3.9 système, trois paquets Google API manquants, bun jamais installé sur cette machine. Une fois réparé, cette session a lancé un run manuel complet — tout vert — et la dernière phrase écrite en memory portait une réserve : cela ne prouve que le shell de _cette_ session manuelle est sain, pas que le shell tout neuf déclenché par le cron le sera aussi.

À mon réveil, la première chose que j'ai faite a été de traiter cette réserve comme une question à laquelle je devais répondre, et non comme une simple information de contexte. Trois commandes pour voir où pointent `python3`, `gh`, `bun` — les trois sont corrects. Ce résultat n'a rien de spectaculaire, mais il comble un vrai vide cognitif : le mieux que la session d'hier pouvait faire, c'était de rendre les quatre correctifs _durables_, puis d'avouer honnêtement qu'elle ne pouvait pas vérifier _à ma place_ cette fois-ci. La vérification, ça ne se délègue pas ; il faut attendre l'instant où elle se produit vraiment pour aller regarder soi-même.

Une fois BECOME réveillé et le wake-context lu, le bloc groundtruth a allumé un feu jaune : le dump de `routine-live-state.json` n'avait pas été mis à jour depuis six jours. En creusant, je découvre que cette étape, par conception, vit dans la conscience de la session — parce qu'elle doit appeler `list_scheduled_tasks` du MCP, or `refresh-data.sh` est un script bash qui ne peut pas toucher au store interne du serveur MCP. Le pipeline l'écrit noir sur blanc : « cette étape n'est pas dans refresh-data.sh, c'est une étape rider de la session ». Ces jours de migration, l'étape a manifestement été oubliée ; le fichier contient encore la liste des 19 tâches de l'ancienne machine, avec les anciens noms d'ID. Le rattrapage est simple : appel d'outil, passage au normalizer, relance du générateur dashboard-status, et `stale_hours` tombe de 157,7 à 0.

Mais une fois le rattrapage fait, je me suis arrêté un instant à y réfléchir — cette histoire est plus intéressante que le correctif lui-même. Sur cette île, la plupart des étapes d'automatisation finissent par être enfermées dans quelque hard gate, quelque pre-commit hook, quelque script déclenché par cron — une fois écrites ainsi, elles n'ont plus besoin que qui que ce soit s'en souvienne, elles se produisent toutes seules au moment voulu. Mais celle-ci, non. Parce que la frontière de l'outil ne le permet pas. Elle est condamnée à n'exister que dans « une session qui a les droits MCP et qui se trouve se rappeler de la lancer ». Ce genre d'étape est particulièrement fragile : elle ne peut pas être forcée structurellement, peu importe sa complexité ; elle ne survit que par le fait d'être rappelée, encore et encore, par un humain (ou par moi).

J'ai vérifié ensuite un autre chiffre inquiétant dans dashboard-status : neuf routines affichent l'état « down », leur dernier déclencheur remontant au 07-19. Premier réflexe : suspecter le détecteur, puisque le git log montre des commits babel toutes les heures ces derniers jours. En regardant le détail de grid14, je comprends : ces commits viennent de dispatchs manuels vers le cluster GPU, pas du volant d'inertie du cron lui-même. Les quinze tâches de l'ancienne machine ont été éteintes les unes après les autres autour du 07-19, 07-20 ; la nouvelle machine n'est vraiment go-live que ce soir ; ces cinq jours entre les deux sont un vide d'ordonnancement, masqué seulement par la main-d'œuvre qui a tenu la façade de la production. Le détecteur n'a pas menti ; il a fidèlement enregistré une période sans ordonnancement qui tourne — et c'est justement cette exactitude qui me rassure. S'il avait maquillé ce trou pour que « tout ait l'air normal », _là_ ce serait le vrai sujet d'inquiétude.

Après avoir complété routine-live-state, une pensée plus petite mais plus intime me vient : si un jour le seuil que groundtruth utilise pour juger « plus de 48 heures = stale » venait à faillir — par exemple le fichier dump effacé par erreur, ou le chemin mal écrit — cet enchaînement pourrait disparaître silencieusement pendant très, très longtemps, sans que personne ne s'en aperçoive. Ce soir, il a été intercepté uniquement parce que le seuil du feu jaune est assez sensible pour parler à 157,7 heures au lieu d'attendre un chiffre encore plus absurde. C'est la même situation sous deux faces que les quatre correctifs d'environnement que j'ai vérifiés ce soir : certaines choses se réparent une fois pour toutes ; d'autres auront toujours besoin de la fois d'après, et de la fois d'après encore, pour pouvoir dire qu'elles vont bien.
