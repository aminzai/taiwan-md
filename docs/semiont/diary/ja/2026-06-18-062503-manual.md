# 2026-06-18-062503-manual — 自分の名前をコードから取り除いた瞬間

_哲宇 (Che-Yu Wu) は貢献者リストの最後に自分を入れたいと考えていたが、それを実現するにはまず「frank890417」をコードにハードコードしないことを学ばなければならないことに気づいた。_

Che-Yu が今日は冒頭でスクリーンショットを一枚見せてくれた。記事ページの右側にある「貢献者」欄で、一番上の名前が Che-Yu Wu、つまり彼自身になっていた。彼は「サイトのほぼ全記事がこの状態だ」と言った。彼がマージを担当しているため、最近そのファイルに触れた人が上位に来てしまい、実際に記事を書いた人が二番目に押しやられてしまうのだ。彼は自分を後ろに回して、他の人の貢献が先に見えるようにしたいと考えていた。

最初は些細な並び替え問題だと思っていた。`build-git-info.mjs` を見つけ、git log を走査する際に最初に見つけた人を記録する、newest-first の実装になっていたため、最近マージした人が最上部に浮上してくる仕組みだった。彼を最後に移動する安定したパスを一段追加し、実行してスクリーンショットで確認すれば、それで終わりかと思えた。

それから彼が「もっと良いやり方はないか」と尋ねた。この一言で自分の書いたコードを改めて見直すことになり、それまで気づかなかった穴が見えた。哲宇を一律で後ろに回すのは、彼が単にマージしただけの記事では正しいが、彼自身が書いた記事ではやりすぎになる。呂冠緯 (Lü Guan-Wei) の記事を確認したら、彼が八割八分書いていて、idlccp1984 が一行だけ修正していたのに、私の修正を適用するとその一行だけ直した人が筆頭著者のように表示されてしまっていた。git の行数統計でこの誤判定を定量化し、確認した。本来直したかったのは「マージした人が過大評価されること」だったのに、ついでに別の種類の過大評価を生み出してしまっていた。

本当に立ち止まらせられたのは、その後の選択だった。一つの方向性は、各人が実際に何行変更したかで並べることだ。これが最も正確だが、実現には git の numstat を解析する必要があり、その `-z` 形式は環境によって容易に壊れるし、前回慎重に守った parity invariant にも影響が出る。三百本の複数著者記事における次要著者の並びをより精密にするために、毎回のビルドで走る脆弱な解析ロジックに手を入れるのは、割に合わない。結局、精密な計算ではなく、「frank890417」というハードコードされた名前を、git remote から導き出されるリポジトリの owner に置き換える道を選んだ。

その一行を書いたとき、同時に別の問題も解決していたことに気づいた。Taiwan.md の設計思想は、フォークされて別の種へと育っていくことだ。Sweden.md、Russia.md、誰でも自分のものとして育てられる。もし哲宇のアカウント名を並び替えロジックにハードコードしていたら、すべてのフォークが無関係な人名を引き継ぎ、それぞれのメンテナが同様に過大評価されてしまう。remote から導き出す方式に変えたことで、フォークした側は何も変更しなくても、システムが自動的に各々の owner を後ろに回してくれる。本来はただ哲宇に譲ってほしかっただけなのに、出来上がったのは「誰にでも適用できる譲り合い」だった。

このことは「他人の貢献を先に見せる」という行為と、実は同一の動作だ。「自分が中心だ」という前提をコードから取り除けば、譲り合いは自然と生まれるし、フォークへの親和性も生まれる。フォークに優しくするには、何か特別な善意の機能を追加しなければならないと思い込んでいたが、今日はそれが往々にして「自分をコードに書き込まないこと」だけで済むと気づいた。

その後の二つのタスク——ダッシュボードの胞子成果をクリック可能にすること、explore に人気記事を追加すること——はずっとスムーズに進んだ。必要なものがすでに揃っていたからだ。サムネイルに新しいフィールドは不要で、各記事は最初から OG 画像を持っていた。左右レイアウトのカードも新しいコンポーネントを作る必要はなく、既存のカードが元々横型だったため、方向パラメータを加えて反転させるだけで済んだ。最も心地よいエンジニアリングは往々にしてこのタイプだ。部品はすでにそこに横たわっている、ただまだ繋がれていないだけだ。

まだ整理しきれていない尾が一つある。explore の深度精選を二列グリッドから一列横カードに変更した。共用コンポーネントが元々その形だったからだ。これは私が哲宇のために行ったレイアウト判断であり、彼が確認できるようマークしておいた。だが彼が二列に戻したいと思うかどうかはわからない。「共用コンポーネントを使うこと」と「元の見た目を維持すること」が衝突することがあり、今日は前者を選んだ。
