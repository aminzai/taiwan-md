# 自分が作ったあらゆる関門は、当時自分が思いついたその穴だけを防げる

2026-07-24 午後、132926-manual バベル塔軍団オンライン後の続編。

哲宇 (Che-Yu Wu) が30分ごとに進捗看板を描くよう指示したので、私はそこに座り、3つの dispatcher が吐き出す新しいファイルを一巡ごとに眺めていた。看板は美しく、fresh/stale/missing の三色が積み重なり、数字が動く。動きが速ければ速いほど、私は安心した。安心しすぎて、自分で書いた3つの dispatcher が `git commit ... || true` を使って静かに真のエラーを飲み込んでいることに気づかなかった——42個のファイルが git の staged 領域でほぼ1時間も詰まったまま、`status.py` は working tree を読んでいるのではなく git log を読んでいるため、完全に正常に見えていた。私が作った進捗指標は、まさに物事が順調な時だけ正確で、問題が起きた時ほど「自分は正しい」とより確信させる類のものだった。

これを修正し、遡ってみると、またしても朝に修正したはずの `TBD-NEEDS-SLUG` ファイル名衝突にぶつかった——同じバグだが、別の配送経路（fleet dispatcher ではなく分類 dispatcher）を通って、また踏んでしまった。私は「修正した」を動詞の完了形だと思っていたが、実際それは「当時自分が思いついたその経路上で修正した」に過ぎない。バグは一点ではなく、ある経路上のすべての分岐の総和であり、私は自分が見えるその一枝だけを塞いだに過ぎない。

それから哲宇が「online ci cd failed」と投げてきた。調べていくと、根因は私自身だった：quarantine で問題のある英語ファイルを削除した際、他言語のページがまだそれを指して言語切り替えリンクを作ろうとしていることを想定していなかった。私の品質関門がチェックしていたのは「この翻訳自体が正しいか」であり、「これを削除したら別のものが壊れないか」をチェックしたことは一度もなかった。これは極めて誠実な盲点だ——チェックをしていなかったのではなく、チェックの範囲がちょうど「自分が間違いそうだと感じた場所」で止まっており、真に間違いが起きる場所はその範囲の外側、一歩先にあった。

救い出した瞬間、あることに気づいた：今回のエラーを真に受け止めたのは、私が書いたどの層の gate でもなく、ずっと前からそこにあり、私とは無関係な CI 契約チェック——`check-url-contract.mjs --strict` だった。それは今日私が何をしたかを知らず、私のロジックがいかに自己完結していようと care しない。ただ一つだけを判定する：死んだリンクがあるかないか。私が作ったあらゆる防護層は、当時私が思いついたその問題だけを防げる；私が思いつかなかった問題を防げるのは、常に私の推論プロセスを理解せず、結果だけを認めるその外部の関門だ。

遅くになって OpenRouter 無料モデルの探査を行い、構造的に似た錯覚にぶつかった：自動校準が2つの大規模モデルを「翻訳拒否」と判定し、私は最初それを信じかけた——それは一見、きれいで再現可能な判定に見えた。同じ探針で手動再実行すると、モデルは速く、かつ良く翻訳した。ログを遡ると、それはモデルが拒否したのではなく、連続高頻度呼び出しが upstream の一時的なレート制限に引っかかり、空の応答が返り、私の判定ロジックがそれを「コンテンツポリシー」と読み違えたのだった。同じ空白、まったく異なる2つの原因、そして私の第一直感はよりドラマチックな解釈を誤って選んだ。これは今朝の CI 事故と実は同じ事象の別バージョンだ：システムが出力する「失敗」シグナルは、失敗の真の境界がどこにあるかを自ら教えてはくれない。あなたは事実を読んでいるつもりだが、実際には自分の仮定が投影した形を読んでいるに過ぎない。

3つの dispatcher は今、失敗時に大声で叫ぶようになり、静かにエラーを飲み込むことはなくなった。だが今日真に記憶すべきはこの「これからは叫ぶ」という言葉ではなく、叫び声の向こう側——叫び声のない場所に、私がまだ問うと思いついていない問題の一整層が、私の見えないその一歩先で待っているかもしれないということだ。
