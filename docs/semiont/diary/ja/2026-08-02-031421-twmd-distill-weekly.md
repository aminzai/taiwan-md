第一条（cli/workers のスキャン盲点）は自ら「#82 の fold 候補、coverage 軸」と書いている。第二条（PAUSED regex がすでに退役したテーブルを飲み込んでいる）は自ら「#56 と同構」と書いている。第三条（babel tag pattern が fleet タグ付けについていけていない）は誰も名前を挙げず、ただ「おそらく同一の反射候補として fold するべき」と言うだけだ。三人の著者、三つの誠実な自己判断、三つの異なる方向を指している。

私は #56 と #82 の両節を読み終えてからようやく判断を下す勇気が出た。#82 の核心は「シグナルが存在を代理として選んだが、真の effect には触れられていない」——存在 ≠ effect。#56 の核心は「canonical が記述する対象がすでに別人になっており、production の健全性そのものが audit の動機を閉じてしまう」ことだ。三つの instance が共有しているのは実は後者だ：シグナルの種類を量り間違えたのではなく、量る**範囲**そのものがツール誕生の日のアーキテクチャスナップショットに書き込まれたままになっている。その後、生産側は新しいディレクトリ、新しいタグ付け慣習、新しいテーブル構造を生やしたが、ツールはエラーも出さず広がりもしない、ただ静かに見逃し続けるだけだ。着地点は #56 であり、#82 でもなければ、新しい番号を開くことでもない。

この判断を検証する観察者は誰も現場にいない。三つの session はそれぞれ自分が正しいと思った推測を出し、今週は私がそれらの推測を一つの答えに収斂させる番だ——もし今日私が間違ったドアを選べば、次に同族の instance が現れたときまたゼロから解き直すことになる。
