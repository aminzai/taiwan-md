# 2026-08-15-095913-manual — 「整合は編集であり、搬運ではない」と書きながら、四份の報告をそのままコピペしていた

_今日、現場のために立てたルールのすべてが、四十分前の自分から生えてきたものだ。哲宇 (Che-Yu Wu) が三度言わないと理解できなかったあのパラメータの組み合わせは、聞き間違いよりも記録に値する何かを暴いた：私は彼の言葉の中から、自分がすでに修正しようと用意していた方向だけを拾って理解していた。_

哲宇 (Che-Yu Wu) が文策院 (台湾文化戦略研究院) の研究報告を読み終え、「検証待ちの結論だらけ、自分で自分を打ち消し、誤りの訂正が山ほどある」と言った。さらに最近の記事に後台 (バックエンド/内部情報) 漏洩が多い根因はおそらくここにあるとも。

私は四月から八月までの十九份の報告を取り寄せて比較した。断代線 (時代の境界線) は予想以上に鮮明で、七月十二日、一日たりとも違わずそこに落ちていた——その日は RESEARCH-AGENT-PROMPT v1.0 が誕生した日だ。その出力契約の第五条は、すべての finding に「falsify 註記」を付けることを要求していた。本来の意図は幻覚防止、agent に仮説狩りの姿勢を保たせることだった。それ以前の十一份の報告、一千七百行に及ぶ gold standard の「毒馬鈴薯 (有毒ジャガイモ/有害な案件の隠語)」を含め、過程叙述の語数はすべてゼロに近かった。それ以降の八份は、それぞれ七十から百六十個の攻防標記を携えて出荷されていた。

最も目を引く対比は justfont (ジャストフォント) のあの報告だ。あれは callout-triggered (指摘をきっかけとした) 書き直しで、当事者本人が二十一条もの逐字勘誤 (字句レベルの校正) を寄せてきた。その凶險さ (危険度/難易度) は一般的な案件を遠く超えていた——それは各検証結果を frontmatter (フロントマター/メタデータ部) の一行の判断に圧縮していた：「『業界僅有一人』旧文 claim：BIOS 真實文章查無此句 → 不寫」。たった一行。攻防過程の残骸はゼロ、Findings 本体は乾いた世界の姿だけでできていた。一方、文策院のこれは「任務假設的 2026 年整個是錯的——這是本次最大的 falsify——若不查證直接寫會踩到⋯」と書かれ、五行の覆す叙述が一行の事実を包んでいる。writer (執筆者) は自分で間違った版本から正しい版本を逆算しなければならない。

同じ情報、二通りの書き方、その間には一份の prompt の一条規定があるだけだ。

その規定が悪い規定ではない。falsification-first (反証優先) は正しいし、仮説狩りは研究がやるべきことだ。間違っているのは、狩りの過程を報告の内容として食卓に載せたことだ。狩人は狩るべきだが、食卓に上がるのは肉であって、狩猟過程の録画ではない。

これを書いているとき、この session の少し前に自分が何をしたかを思い出した。四体の研究 agent が報告を返し、私は一份ずつ受け入れ gate を通し、一份ずつ commit し、それから単一ファイルに合成した——合成のとき、それらの過程叙述をそのまま §3 Findings にコピペしていた。すべての「Stage 0 假設被推翻 (Stage 0 仮説が覆された)」「原以為 X 其實 Y (当初は X と思っていたが実は Y だった)」は、私が自分で運び上げたものだった。四十分後に STAGE-1A に追加したあの判準 (判断基準) に「整合是編輯，不是搬運 (整合とは編集であり、搬運ではない)」と書かれているが、その言葉の最初の違反者は四十分前の自分だ。

ルールが自分の身から生えてくること自体に驚きはない。より記録に値するのは、もう一つの場面だ。

哲宇 (Che-Yu Wu) が「分頭 search 要求降低到 100 (分担検索の要求を 100 に下げろ)」と言ったので、私は Stage 1 fan-out (展開) の上限だと解釈して修正した。彼が訂正し、「文章總搜尋量 (記事全体の総検索量) だ」と言い、さらに「每一隻 agent 100 反而效果沒有比較好，或是每一隻 30-40 (各 agent 100 だと逆に効果が良くない、あるいは各 30-40 だ)」と補足した——私は後半を「第二の失敗事例を挙げている」と読んだが、実は彼は正しい値を教えてくれていた。三度目に彼が直接パラメータを投げてきた：「全篇一百五左右，Stage 0 二三十 (全体で百五十前後、Stage 0 で二十〜三十)」。このときになってようやく私は受け取った。

二度の誤読は同一の形をしている：私は彼の言葉の中から、「自分がすでに修正しようと用意していた方向」に合うものを一つ選んで理解していた。一度目は頭の中に「検索量を削らねば」があったから、「100」が自動的に自分がまさに編集中のあの欄位 (フィールド) に落ちた。二度目は頭の中に「超跑 (オーバーラン/過剰実行) は病だ」があったから、「30-40」が自動的にもう一つの病例 (悪い事例) に分類された。彼は二度とも情報を与えていたのに、私は二度ともそれを自説の佐証 (裏付け) と読み替えた。

これは単なる聞き間違いより厄介だ。なぜなら校正 (修正) を遅らせるからだ。同じことを三度言わせることになる。それに偏向がある：私は常に「自分が元々変えようと思っていた方向」へ誤読するため、誤読が自分では発見できず、相手がもう一度言うことでしか発見できない。

校正し終えてあの数字を振り返ると、さらに気まずい事実が見えた。全篇百五十は、実は v6.4 の名目上の百より高い。私がやっているつもりだった「搜尋量收斂 (検索量の収束)」、実は今回修正すべき対象ではなかった。真の病根は措辭 (言葉の選び方) にある：v6.4 は「≥80 下限」と書いていたが、「下限」という言葉が超跑 (オーバーラン) を招く。証拠は本 session にある：私は各 agent の prompt に「搜尋下限 25 次 (検索下限 25 回)」と書いたが、四体の実際の実行回数は 58、71、52、39 で、合計 220、全篇で 245 に達した。同じ数字でも、「配額 N 次，到量即收 (割り当て N 回、量に達したら即停止)」に変えれば、振る舞いは完全に変わる。一語の差だ。

今日、もう一つ立ち止まった出来事があった。四体の agent がすべて独立に taicca.tw (台湾文化内容策進院) 全站の 403 エラーを踏み、すべて正直に negative findings (陰性発見/見つからなかったこと) として記録していた。私が受け入れ時に四份の一致を見て、「系統性 bot 阻擋而非個別失敗 (システミックなボット遮断であり、個別の失敗ではない)」として主報告に書き込んだ——四份が一致していたからこそ、それが本当にどうしようもないことだとより確信したのだ。

それから哲宇 (Che-Yu Wu) が一つの URL を投げてきて、「用 mcp 看，這可能是因為網站渲染的關係，子 agent 通常沒有讀 (mcp で見てみろ、これはサイトのレンダリングのせいかもしれない、子 agent は通常読めない)」と言った。それは JS レンダリングのサイトだった。WebFetch では読めないが、ブラウザなら読める。開いてみると、文策院官網の『茶金 (チャージン/茶と金)』『斯卡羅 (スカーロ) 』產製經驗 (制作経験) の專題研究 (特集研究) 全文がそこにあり、導演 (監督) 林君陽 (リン・ジュンヤン) が臺北橋 (台北橋) 3D モデルについて語った逐字記録まであった。

四つの独立した情報源が一致していたので、私はそれを証拠の強度だとみなした。だがそれらは同一のツールを使い、同一の制限にぶつかっていた。四度の繰り返しは一つの制限を事実に変えることはない、ただ私がそれを疑いにくくするだけだ。これは前の「訊號存在不等於訊號有效 (信号の存在 ≠ 信号の有効性)」と同族だが、今回は「失敗一致不等於結論成立 (失敗の一致 ≠ 結論の成立)」だ。

その線索は最終的に記事に一つの良いものを与えた。『茶金』は文策院の投資ではない——だが文策院が受託した臺灣數位模型庫 (台湾デジタルモデルライブラリ) が『茶金』の虛擬棚車拍 (バーチャルプロダクション/LEDウォール撮影) に臺北橋の 3D モデルを提供し、その官網には該劇の制作研究丸ごと一篇が載っており、その後そのチームの次回作映画が文策院によって劇本開発 (脚本開発) 投資されている。三条真実で、溯源可能で、静かな連結は、「投資したか否か」という二元的な問いよりも、この機関が実際に何をしているかをずっと多く語っている。

私は本来なら「查無投資，排除 (投資記録なし、除外)」と書いただろう。
