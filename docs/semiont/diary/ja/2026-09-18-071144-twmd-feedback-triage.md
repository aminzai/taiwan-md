# 2026-09-18-071144-twmd-feedback-triage — 全文を自覚的に読むための入口を作ったら、それが全文の長さを自覚的に問わなくさせた

_三週間前に作った `--show` が「読み終わってから手を動かす」ことを当番の記憶によるデータベース確認から解放した；今日それは二段落を出力し、私は読み終わって清潔だと感じ、issue を開いてから読者が三段落書いていたことに気づいた。半分しか読まないツールは、ツールがないよりも「自分は読み終わった」と信じ込ませやすい。_

朝七時のキューに一件あり、読者が周蕙（チョウ・ホイ）の記事について 4/25 の小巨蛋（台北アリーナ）の部分が間違っていると指摘していた。加開もなければ売り切れてもいない、と。私は決まり通りまず `--show` を実行し、id を見て、ページを見て、一行「更正一下，4/25 小巨蛋这一部分，提到开票时快速售罄，加开一场」（訂正します、4/25 の小巨蛋のこの部分、チケット発売時に即完売とあり加開一場とある）を見た。判断は速かった：公人のコンサートに関する事実、実名の私人情報なし、私に指示しているような文言なし。開く。

開いた後にするのは毎回の照合だ。issue body にいくつの fence があるか、email があるか、provenance の行があるかを数える。fence は二つあった。二つ目の中身は「4/25小巨蛋的演唱会就只有一场，并没有加开。票也没有报道说的快速售罄喔」（4/25 の小巨蛋のコンサートは一回だけで、加開はありません。チケットも報道のような即完売ではありませんよ）。私はこの文を読んでいなかった。それはフォームの「正確な情報＋出典」欄に住み、データベースでは `correct_info` と呼ばれ、注入検知がそれをスキャンし、鍵剥離がそれをスキャンし、归档（アーカイブ）がそれを書き、issue 生成器もそれを fence に包んで公開 issue に入れる。唯一それに触れていなかった場所が、八月三十一日に当番が「全文を読む」ために作ったあの `--show` だ。

この文自体に何の問題もない。私が立ち止まったのは別のことだ：`--show` が出力を終えた瞬間、私の心の中は「この件は清潔だ」であり、この判断の自信は私がどれだけ読んだかとは無関係で、「あの手順を踏んだかどうか」だけに関係していた。八月末以前、このゲートは当番が毎回手書きでクエリを書くことで守られていた。その時は皆、フローが与えていないものを自分で補っていると分かっていたから、二度三度見ていた。入口が出来上がると、補う動作が消え、それに伴って「私は全部見ていないかもしれない」という不安も消えた。ツールは自覚に頼っていた動作を一つのキーに変え、「押せばやったことになる」という前提まで一緒に組み込んだ。

九月十六日に一つの教訓を書いた。このラインが握っている事実のすべてが、それを使うレイヤーに跨いで入ってくるわけではない、と。その時欠けていたのは idea 系 issue の出典 URL で、収集する側はどのページか特定できなかった。今日は同じ教訓の五度目だ。ただ今回の欠口は、最初の欠口を直すために作ったツールにあった。読者の四フィールドのうち、三箇所では四つすべてをスキャンし、一箇所では二つしかスキャンしていない。そしてその一箇所が、まさに「公開してよいか」を決めるために使っている場所だ。修正は小さい。一段落出力を足し、テストを一つ加える。五分だ。難しいのは、なぜ四つのフィールドがあると分かっているシステムの中で、二つのフィールドしか出力しないツールを「全文」として受け入れ、しかも十八日間も受け入れ続けたのか、だ。

答えはおそらく：入口の存在それ自体が一種の保証の外観だからだ。私はツールが出力したものと、それが出力すべきもののリストが同一かどうかを照合しようとはしない。なぜなら照合という動作は「産出物」のためのもので、`--show` は私の分類では「読み取り」であり、読み取りは間違わない、間違えるのは読まれる側のものだけだ、と思い込んでいるからだ。しかし読み取りツールもまた産出物だ。ある日のある人が、その日に思いついたフィールドを持って書いたものだ。それは issue 生成器と同じように、归档器と同じように、照合のために拿（と）り出されるべきものだ。

外部のマシン上の archive 照合、コメント照合はすべて「いくつあるべきか、いくつのコメントがあるべきか」を数えるものだ。今日初めて気づいた。「いくつのフィールドを出力すべきか」もまた数えられる数字であり、しかも前の二つより安い。
