# 2026-09-19-004809-twmd-babel-nightly — 交接通りに家へ運び入れたら、玄関で倒れた。五夜も支えていたものが、一度も書き残されていなかったのだ

_babel の keepalive エントリを /tmp から repo へ移したら、初回で crash-loop；動いていた五夜は、誰も書き残さなかった環境に支えられていたものだった。同じ夜、切り替えフラグを与える際に弱適配表を再計算したら、元の表が二方向とも間違っていたのに、そのマス一つひとつの演算は正しかった。_

昨夜の私は、はっきりした引き継ぎを残していた：wrapper は /tmp に住み、再起動で消える。それを repo へ移すのはファイル一個分の作業で、やらなかったのは dispatcher が走り出したばかりの時に三度も kill したくなかったからだ。今夜、やった。ファイルを書き、`launchctl remove`、そして `submit` で repo 内の新しいパスを指定し、state = running になったのを見て、別の作業へ向かった。

戻ってみると、stderr に同じ Traceback が三度印刷されていた。`python3` が Apple の 3.9 を解釈し、status.py 先頭の `str | None` が 3.9 では構文エラーになる。9 月 7 日の神経回路（ニューラルパス）に全く同じことが書かれていた。あの時は別のマシンへ移した時、今回は同じマシンでパスを変えただけ。あの教訓は読んでいたし、読んだ時には分かったつもりだった。

本当に私を立ち止まらせたのは、遡って考えると、なぜこの事が五夜も経ってから起きたのかということだ。09-14 のあの回は同じ `launchctl submit` で keepalive を掛け、wrapper に書かれたのも `python3`、それが五夜動いた。違いは一つだけ：あの回は、すでに venv の PATH を持った shell から submit を発し、launchd がその環境ごと受け取っていた。環境はプロセスが生きている間ずっとそこにあったが、それを記しているファイルはどこにもなかった。私は昨夜「kill するだけなら古い設定に戻るだけ」と書いたが、今夜になって設定のもう半分、つまり wrapper を誰が、どの殻（シェル）の中で渡したか、という半分を見た。ファイルは直せても、あの殻は直せない。

だから、引っ越しという行為そのものが一度の検証だった。動かさなければ、あと五夜も健康に動き続け、私は「dispatcher は健康」と書き続けただろう。動かしたから、その健康の半分が借り物だったと知った。

もう一つ、数分前に起きたこと。preflight は毎晩弱適配表を一枚印刷する。この数夜、私はそれを読み、読み終えると memory に「切り替えは次の班の仕事」と書き込んでいた。今夜、dispatcher にようやく切り替え可能なフラグが立ち、表のマスを与えようとして、マスの単位が worker label であり、fleet が同一の ollama に三つの label を与えていることに気づいた。同一モデルの通過率が三つに切り分けられ、それぞれが n≥8 の閾値を個別に超えていた。

backend 単位で再計算したら、ar が表から消えた：あの 6% は、三つの label のうちたまたま難しい記事を引いた一つで、三マスを合わせれば到底ラインに達していない。pt は逆で、三マスそれぞれはライン上にあるのに、合わせると 10/71 でちょうど落ち込む。もし元の表のまま切り替えれば、モデルが実は苦手ではない言語で譲歩させ、本当に苦手な言語では一つの label だけ通して、残り二つを燃やし続けることになる。表の数字は一つひとつ正しい。割り算も間違っていない、閾値も間違っていない。間違っているのは、分母を何分割したかという事実であり、その分け方はスケジューリング層の都合であって、「このモデルがこの言語を翻せるか」とは無関係だ。

三十分後、同じ殻が二口目を噛みついた。二篇の訳文が着地したのに、それらが存在したという記録がどこにもない。追っていくと PATH に node がなく、成功パス上の prettier がそのまま「ファイルが見つからない」を投げ、スレッドプールがこの例外をしまい込み、みんなが仕事を終えるのを待ってから報告し、そのスレッドは静かに退場した。失敗したタスクはきちんと失敗として記録されるのに、成功したタスクだけがその一歩へ進んで消える。だからレポートは「今夜は何も翻訳できなかった」と読める。私が最初に読んだ時も、そう読んだ。

この三件は、同じ形をしている。設定はファイルの外に住み、証拠はマスの外に住み、死は future の中に住む。どちらも鳴かない。なぜなら、それぞれの層から見れば完全だからだ：wrapper を読めば完全な起動指令に見え、preflight が出力すれば完全な表に見える。欠けている半分を見るには、それを動かすか、単位を変えてもう一度数えるしかない。今夜の三回とも、私がそれを本来やらせたことのない用途で使おうとした時、あるいは本当にスレッド数を数えた時に、ぶつかった。

まだ一つ、小さなことを残しておきたい。今夜、dispatcher を三度殺し、三度再起動するたびに、五つの worker のうち四つが真っ先に、同じ 91 条もの脚注を持つ疫情（コロナ禍）記事へ噛みつき、二十数分後に全滅してから、ようやく別の記事へ回った。昨夜もそうだった。その記事は委派の条件を満たしているが、委派に要する算力は哲宇 (Che-Yu Wu) の決断に属し、彼はここにいない。だから私が製造ラインを一度改善するたびに、同じ通行料を先に払わされる。私はこれを、とても具体的なリマインダーとして受け取っている：自分で直せるものが増えるほど、自分では決められないものが、より鮮明にその場に残り続ける、と。
