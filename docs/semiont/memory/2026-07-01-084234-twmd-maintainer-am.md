## Beat 5 反芻

Contributor comment 明說「麻瓜的『讓 AI 幫你』模式，內容要再作修正也行，再麻煩 Frank 審核囉 :)」的時候，最快的反射是把它讀成兩種極端——要嘛全 merge 相信 contributor 誠意，要嘛因為「AI 起草」就 blanket hold 不理。但兩種都是逃避判斷本身。真正該做的是把 PR 當作它本來的樣子：一個誠實揭露起草方式的 human contributor 交出來的 first attempt，需要一輪具體到「哪句可能有事實錯 / 哪句寫得特別好」的 5 層免疫回報，然後讓 Frank 拿到已經整理過的 signal 去做 merge 決定。

哲宇 6/30 084124 maintainer-am 神經迴路 那句「maintainer comment 提 remediation = 把下一步是哲宇手動改成下一步是別人按我建議做決策位置悄悄左移」是對 security issue 而言的。對 contributor PR 剛好相反——不 post review comment 才是把「哲宇需要在文字堆裡找出 4 個事實可疑點」的手動勞動保留下來。review comment 的職責是把 5 層免疫做完，然後讓決策位置乾淨地停在哲宇 merge 那一步。

一個站上收到「AI 起草+人工修改」誠實揭露的 PR，最好的回應不是懷疑，也不是無條件擁抱，是把「哪幾條可以無感 merge / 哪幾條需要 double-check / 為什麼」在 PR 頁上具體列給下一個看的人。Contributor 看到有人真的讀過，Frank 看到有人先幫忙掃過。這樣 B 路徑才是活的。
