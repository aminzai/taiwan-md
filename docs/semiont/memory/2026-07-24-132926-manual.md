## Fleet 上線 + 同一批次連續修 6 個系統性缺陷

這是本 session 的核心工作，也是哲宇明確要求的新模式：發現缺陷不等批次跑完才修，當場修好、驗證、寫回 canonical 工具再繼續。派發 3090（`gemma4:12b`，id→hi）與 4090（`gemma4:26b`，vi→pt）之前，第一次 `prepare-batch.py` 就抓到 262/300 篇會因缺 `--slug-map` 而撞同一個 `TBD-NEEDS-SLUG.md` 檔名，動手前攔下，用 `_translations.json` 反查既有 en slug（862/862 覆蓋，零 LLM call）解決。

接著審查今早已 commit 的 ja P1 批次（ollama-only，因 codex 當時不可用），發現 6/8 篇掉了 image 系列欄位、1 篇 tags 原樣抄中文未翻、1 篇 readingTime/lastHumanReview/featured 被錯誤加引號（會讓 Astro 的 Zod schema 靜默壞掉），外加 1 篇的圖片來源清單掉了 3 個 markdown 連結語法加 1 個 URL 被改壞一個字（女孩→女孤，死連結）。全部手動修回（`b8930b3c1`），順便把 `verify-translation.py` 從 en-only 工具泛化成任何語言都能用的 hard gate：CJK-script 目標（ja/ko）改用「跟 zh 源檔逐字相同」判斷，因為「含 CJK 字元」對 ja/ko 本來就是正常現象，抓不到問題。

fleet 剛跑起來時 4090 對每一篇都是 2 秒瞬間失敗，查到根因是 Ollama 在沒有明確帶 `num_ctx` 時會用自己伺服器端的預設值（觀察到約 4096），完全不理會模型卡宣稱的 context length。一個 35K 字的翻譯 prompt 被截到 `prompt_eval_count=4095`，模型只看到被砍斷的指令，吐一個字就停了。改 `backends/ollama.py` 依實際 prompt 長度動態算 `num_ctx`（`11ba07af2`）後，同一顆節點同一篇文章從瞬間失敗變成正常跑完。

## 站上四個新語言首頁半年顯示中文的 bug

查「為什麼 vi/id/pt/hi 首頁功能介紹區塊還是中文」時，用 curl 直接對照發現 `src/i18n/ui.ts` 這四個語言的 block 裡，16 個子 bundle 的 spread 全部寫死指向 `['zh-TW']`，是四語還在 disabled scaffold 階段時留下的殘留寫法。2026-07-18 23:14 「四語介面字串全量落地」那個 commit 把 `home.ts` 等 16 個 bundle 檔案本身翻好了，卻沒人把 `ui.ts` 的 spread 引用改過來，於是內容早就翻好卻沒接上。改完（`d8a42970a`）在本機 dev server 驗證 `/vi/` `/id/` `/pt/` `/hi/` 四個都正確顯示母語首頁文案，push 上線。

同一輪順手發現 `subcategory-i18n.json`（terminology 頁與 graph.astro 節點用的分類標籤翻譯表）只涵蓋 103/229 個 zh 分類值，且完全沒有四新語言。原本我把 zun.md 的 subcategory 從日文改回中文當「修正」，被哲宇糾正：subcategory 是要被翻譯的呈現層標籤，不是要跟 zh 完全一致的內部鍵。改正方向後，用既有已翻譯文章的多數決資料補齊 en/ja/ko/es/fr 的缺口（純資料挖掘、零 LLM call），vi/id/pt/hi 全部 229 條交給 9 個平行 sub-agent 翻譯（`4bbef3cb8`）。過程中 5 個 sub-agent 撞到 session usage limit 中途斷線，resume 後發現大多數其實已經寫完檔案只是沒回報成功，這跟今早死掉的本機 dispatcher 是同一種失敗模式，都是「執行環境的額度／生命週期跟工作本身脫鉤」。
