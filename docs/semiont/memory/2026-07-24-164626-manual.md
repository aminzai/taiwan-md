## 三個 dispatcher 撞見的三個新缺陷

在畫進度看板的過程中，先發現一個比想像中嚴重的問題：三個 dispatcher 的 commit 步驟一直用 `git commit ... || true`，那個 `|| true` 把 pre-commit 的真實拒絕（一篇文章 15 處腳註格式違規）整個吞掉，`git add` 照樣執行，於是 42 個檔案在 staged 區卡了將近一小時——`status.py` 讀的是 working tree 不是 git log，看起來進度很正常，實際上什麼都沒真的落地。回頭看，我自己的 `verify_group` 閘門只查內容正確性（翻譯完整、無中文洩漏），沒查站上自己的格式慣例，兩層標準不一致，通過內容關卡的檔案卡在格式關卡。

同一輪還在分類 P1 stale 情境撞見我以為早上已經修掉的 `TBD-NEEDS-SLUG` 檔名碰撞——quarantine 刪除一篇已 commit 的 en 檔會讓它從「stale」變成「missing」，但分類 dispatcher 的 `prepare-batch.py` 呼叫沒帶 `--slug-map`（fleet dispatcher 那條路徑已經補過，分類這條路徑漏了）。這次四篇分別落在不同分類資料夾，沒有真的互覆蓋，但邏輯是一樣的地雷。

把三個 dispatcher 全部重寫成 v3：`verify_group` 加一層 `article-health.py` 檢查、`git_lock_commit` 改成失敗會印出來並且自動用 article-health 隔離違規檔再重試一次，不再靜默吞錯；分類 dispatcher 補上 `--slug-map`。恢復卡住的 42 個檔案時順手發現 es 語言那批今早的舊帳也還沒清——12 篇 es 翻譯已經在 working tree 待了四個小時沒 commit，跟同一批 ja/ko 一樣的問題（image 欄位掉失），修了 8 篇、隔離 4 篇需要重翻的。

## CI/CD 連續失敗又救回

哲宇一句「online ci cd failed」讓我去查，發現部署已經連續紅燈三次。根因追到我自己：quarantine 刪除 `en/About/founder.md` 之後，其他語言（es）頁面的 hreflang 標籤還指著那個現在不存在的 EN 頁面——hreflang 產生器假設每個啟用語言都有對應檔案，不檢查存在與否。另外還撞見一個獨立的程式碼 bug：vi 跟 id 新翻的《文章如何誕生》這篇，hreflang 指向 zh-TW 版本的網址用錯了 slug，因為 zh-TW 源檔沒有明確的 `slug:` 欄位，真正的網址是原始中文檔名，不是其他語言共用的拉丁字母 slug。這是站上程式碼第一次被新語言的翻譯踩到，不是翻譯內容的問題，根因還在 `src/components/SEO.astro` 跟 `src/utils/getLangSwitchPath.ts` 裡沒修。

用 `git show` 把 founder.md 從 quarantine 之前的 commit 復原回來（寧可 stale 也不要 missing），把兩篇踩雷的 vi/id 版本也隔離掉，本機真的跑一次 `npm run build` 確認 dead link 數字從 3 掉到 0 才敢 push。部署恢復綠燈。

## 開始建 OpenRouter 免費模型自動探勘

哲宇丟來 OpenRouter 排行榜截圖，要我「完整進化 translation fleet」並且「auto-quality model discover」找免費好模型擴大平行度。那張圖是付費用量排行榜，不是免費層清單，兩者完全是不同的東西——直接打 `/api/v1/models` 拿到目前真正的免費層庫存，15 個，跟排行榜上的名字幾乎不重疊。寫了 `discover-free-models.py`：先用既有 pipeline 的排序原則（西方廠商優先、避開中國廠商、避開太小/太專精的模型）排序候選，再跑一個輕量校準（主權敏感探針 + 一般翻譯 sanity check）。第一輪跑出來 nvidia 的兩個大模型顯示「拒絕」，但手動重試發現其實翻得很好——是短時間內連續呼叫撞到 upstream 瞬時限流，不是真的拒絕。已經在腳本裡加了重試機制，重新校準的結果還沒跑完就被哲宇的收官指令打斷，留給下一個 session 接手。
