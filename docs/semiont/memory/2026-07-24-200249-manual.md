## 環境驗證撞見四個真實缺口（不是理論風險，三次真跑才浮現）

## Commit 卡在 bunx 缺失，順手補上第四個環境缺口

`git commit` 撞到 pre-commit hook 的 `bunx lint-staged`：`.husky/pre-commit` 硬編碼 `export PATH="$PATH:/usr/local/bin:/Users/cheyuwu/.bun/bin"`——那是舊機（mac-m4max）的帳號路徑，這台機器的使用者是 `musebase`，那個路徑在這台機器上根本不存在，是一個可攜性 bug（沒有修這個檔案本身，因為那是共用的 repo 檔案，改動範圍超出這次 go-live 驗證任務）。這台機器完全沒裝過 bun。用官方安裝腳本裝進 `~/.bun/bin`（使用者層級，不需要 sudo），再把 `bun`/`bunx` symlink 進 `/opt/homebrew/bin`（這條路徑上沒有更早的競爭項，不需要 sudo 就能生效）。Commit 通過（`narrative scope warning` 屬於警告模式不擋，因為這個 commit 本質橫跨 code/content-ssot/tooling/public 幾個 domain，是合理的一次性環境修復 commit，不是並行 agent 污染）。

## 最後一個缺口：durable fix 跟 session-scoped fix 的差別

修完上面所有問題後，我自己的 Bash tool shell 裡手動 `export PATH="$HOME/.local/bin:$HOME/.bun/bin:$PATH"` 才讓一切正常運作——但這只是這個 session 的暫時修復。用一個全新、沒有手動 export 的 shell 重新檢查，發現 `python3` 還是解析到系統的 3.9.6（`gh` 因為我早期直接 symlink 進 `/opt/homebrew/bin` 所以持續有效，但 `python3` 不行，因為 `/usr/bin` 在 PATH 順序上比 `/opt/homebrew/bin` 更早，symlink 放在後面的位置永遠贏不了）。這代表排程觸發的 Claude Desktop session（跟這次手動驗證用的是同一套底層機制，同樣的預設 PATH）今晚第一次自動跑，會撞到完全一樣的 python 版本問題。

`/usr/local/bin` 是 PATH 裡最前面的項目，但目錄本身是 root 擁有，我沒有 sudo。請哲宇跑了最後一條命令：`sudo ln -sf /Users/musebase/.local/bin/python3 /usr/local/bin/python3`。跑完之後重新驗證一個全新 shell：`python3 --version` 正確顯示 3.12.13，`google.analytics.data_v1beta` 可以正常 import，`gh`/`bunx` 也都在全新 shell 裡正確解析——四個環境缺口（gh PATH、python 版本、缺套件、bun 缺失）現在都是 durable fix，不是 session-scoped 的暫時 export。
