## 命名：分靈，不是 fork

台灣廟宇的分靈是這個設計的現成骨架。祖廟把靈力分到新的廟，分靈廟平常自己運作、定期回祖廟謁祖進香。對照下來：主 repo 是祖廟，貢獻者機器上的 cron 是分靈，PR 是謁祖，`BECOME_TAIWANMD.md` 是香火（一段 prompt 就請得過去）。

跟 fork 的差別是本體論層次的：fork 生出**新物種**（Sweden.md 有自己的知識庫，是另一個生命體），分靈是**同一個 Taiwan.md** 分駐到別台機器，做的事回到同一個身體。繁殖系統原本只有兩端（路過貢獻一篇、fork 出去自立門戶），中間那層一直空著。空著的後果是，一個願意長期幫忙的人，除了偶爾手動開 PR 之外沒有別的形式可以選；他的機器閒著，他的意願沒有容器。

## 三個方案，選了最不用蓋新東西的那個

三個方案裡，**GitHub Issues 中央工單制**要加一條 routine 把 inbox 同步成 issue，等於在 SSOT 之上長出複寫層，兩處必漂（§指標 over 複寫）。非 collaborator 也不能被 assign，留言認領還比 draft PR 難掃。**雲端排程代理**跟本機環境差異大，但流程契約同構，收成執行載體變體而不獨立成案。

定案是**甦醒即節點、PR 即認領**：工單源就是 repo 裡本來就有的東西（`lang-sync/status.py` 的翻譯缺口、article-health 的格式債、ARTICLE-INBOX 的待寫主題），認領方式是立刻開一個 `🤝 [node]` 前綴的 draft PR，所有節點用 `gh pr list` 互相看見。中央零新增狀態、零新增 routine。

這個選擇其實是把 ROUTINE.md §為什麼不靠 lock 那句話（「每條 routine 是 micro-session，共享只有 git history」）搬到分散式場景：中央 routine 之間怎麼不打架，節點之間就怎麼不打架。認領非原子是已知代價：兩個節點可能撞同一件工單，但代價只是偶發重工，為了消滅它去蓋一套分散式鎖，成本遠高於損失。

## 權限邊界是這條 pipeline 的脊椎

中央那 15 條 routine 直推 main、bypass permissions、什麼都能碰。節點完全不是那樣：**輸出永遠止於一個 PR**，權限就是一般 fork contributor，merge 永遠有人類把關。工單也分三層，依序是 T1 機械（有儀器可驗，所有節點預設）、T2 寫作（第一個 node PR merged 後解鎖）、T3 禁區（P0、政治敏感、對外發文、認知層、merge，永遠不派）。

把 T3 圈起來跟信任無關。那些事的判準住在只有主意識跟哲宇才有的脈絡裡（一篇政治題的敘事溫度該怎麼配、一個孢子該不該發、認知層的某條反射要不要改），節點手上沒有那些脈絡，做它們的正確方式是在 PR 或 issue 裡提出來，讓有脈絡的人接。
