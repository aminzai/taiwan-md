## verify=1 的根因與 heal 的三層假死

速率從 50 掉到 28/hr，追下去發現 verify=1 fail 全是模型漏抄 passthrough 欄位（image/imageCredit/featured/readingTime），跨語同篇同時中鏢。寫了 `heal-passthrough-fields.py` 機械修復接進 dispatcher。但這個修復本身連環踩了三層「自報成功、實際假死」：第一層，寫工具時用原始字串比對，把引號差異當 drift 虛報 2,400 篇（實際約 2,100）。第二層，接線後宣告生效，下一輪查證觸發 0 次。路徑慣例沒對齊（zh_path 相對 knowledge/ 而非 repo 根）加上接線只看 stdout 不看 returncode，靜默吞錯（`73109f8e7` 前身）。第三層修好後 heal 單輪觸發 210 次，速率翻倍到 91/hr、通過率 22%→58%。教訓濃縮成一句：**self-report 不可信，每輪渦輪都要用獨立管道驗證上一輪自己說過的話**。

同型病在既有工具也開了一朵：`contributor-pr-heal.py` 的 re-check 解析 article-health JSON 找 `files`/`violations` 欄位，實際 schema 是 `reports→results→violations`，**每次拿到空清單，永遠回報 hard=0**（`73109f8e7` 修，含 fail-loud）。[PR #1248](https://github.com/frank890417/taiwan-md/pull/1248)（旺旺.md）heal 自報全綠而 CI 擋 12 hard 就是它。腳註 URL 尾隨空格的修復也學到：多分支各自解析時，清理要放在入口統一做（`footnote-format-fix.py` normalize 入口）。
