## 不該重啟——以及我自己的探針說了謊

三重巡檢查出產線 21:29 起全數存活且在產出。`babel-dispatch.py` 最後一次改動（21:25）早於產線起跑，`translate.py` 的 armor 修復與 ar/ru 忠實度檢查器都是每篇重新 spawn 的熱路徑。照 [BABEL-VORTEX-LOOP §重啟有成本](../../pipelines/BABEL-VORTEX-LOOP.md)，這種情況重啟純虧。哲宇選「先收尾快照再重啟」。

等待期間我寫了一支 drain 監看，用 `kill -0` 判斷 worker 死活，並且 `2>/dev/null` 吞掉錯誤。它在第一輪就回報全數收工，實際上三隻 vi worker 還在跑，最深的一隻已經 33 分鐘。背景指令跑在沙箱裡，`kill -0` 送不出訊號回 EPERM，被我的 `&&` 讀成「行程已死」。用 `ps` 交叉比對才抓到。前景跑同一條指令是正常的，所以這個假象只在背景出現。改成 `ps -p` 並讓探針先對自己自驗才敢用。**一個吞掉 stderr 的探針，把權限錯誤變成了它要偵測的那個狀態**。

## 純中文檔名的文章排不進翻譯佇列

當輪的自動進化動作抽隔離樣本時，發現 8 個 `TBD-NEEDS-SLUG.md` 已經被 commit 進版控（來自 21:13 那次孤兒搶救）。裡面是四篇好譯文（台灣鐵道史、八點檔、小北百貨、旺旺），全共用同一個佔位檔名，同分類同語言的下一篇會直接覆蓋前一篇，網址還是 `/es/lifestyle/tbd-needs-slug`。

追到根因：`build_slug_map()` 只讀 `_translations.json` 裡 `en/` 開頭的條目，而它自己的 docstring 就寫著「slug 與目標語言無關」。一篇檔名純中文、英文版還沒生出來的文章因此拿不到 slug，ASCII fallback 把非 ASCII 全刪光得到空字串，落成佔位檔名，dispatcher 的守門再把它整個跳過。**沒有英文版就沒有 slug，沒有 slug 就連英文版都翻不出來**，27 篇卡在這個死結，包括唐鳳、莫那·魯道，和前兩天剛上線的台灣鎢供應鏈與苯駢芘食安事件。

我第一次向哲宇報告時說這 27 篇「在十一個語言都是隱形的」，講過頭了。查下去 23 篇其實早有 canonical slug 躺在 ja/es/fr，唐鳳一直都是 `audrey-tang`，真正哪個語言都沒有的只有 4 篇。改成讀全語言、en 優先之後 23 篇當場解套。剩下 7 篇的 slug 寫進新的 `knowledge/_slug-map.json`，優先序最低，不會搬動任何已上線網址。同時擋掉佔位檔名回流（它已經被寫進 `_translations.json`，餵回去會擴散到該文章的每一個語言），8 個檔案改回正確 slug（`8c08b72c0`，12 檔，scope 驗過 0 deletions）。

`rescue-orphans.py` 補上同一道守門。dispatcher 早有這道檢查，搶救路徑當初沒跟著收斂，這是本週第三次「同型病只修了一個呼叫端」。

驗收看的是活產線而不是我的測試：重啟後的 run dir 產出 869 條 slug、零佔位、`prepare-batch` 從 exit=2 變 exit=0。12 小時後檳榔十一語全上、八點檔 10 語、小北百貨與旺旺各 9 語，約 42 篇十二小時前結構上不可能存在的譯文。
