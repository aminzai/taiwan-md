## 文策院走到投影藍圖

研究推翻了幾個進場時的預設，其中三個會直接改變文章的寫法。「文化黑潮」是史哲部長 2023 年另一個計畫的名字，跟鄭麗君催生文策院的 2017-2019 那條線隔了三任部長。《模仿犯》《茶金》《通靈少女》都不是文策院投資案，大眾記得的台流代表作跟它實際投的東西是脫節的，這個落差後來變成投影骨架的第四節。早先流傳的「288 億」全網查無，判定誤植。

persona 稽核有一個收穫值得記：社運參與者與體制內公務員兩個不相干的原型，各自撞到同一點，也就是現任董事長由監督機關文化部的政務次長兼任這件事。這是核心矛盾最具體的物理化身，原本被我放在人事年表裡當一行字，藍圖裡拉出來單獨點名。

《茶金》那條後來還有續章。哲宇丟了一個 taicca.tw 網址說「用 mcp 看，這可能是因為網站渲染的關係，子 agent 通常沒有讀」，一句話同時解掉四份研究報告共同的 negative finding（taicca.tw 全站 403）。它是 JS 渲染站，WebFetch 讀不到，瀏覽器讀得到。用 Chrome MCP 拿到專題研究全文後，《茶金》與文策院的關係比二元的「有沒有投資」細緻得多：文策院承接的臺灣數位模型庫提供了臺北橋 3D 模型給該劇的 LED 虛擬棚車拍（導演林君陽逐字）、官網有整篇該劇產製經驗的專題研究、後續湯昇榮團隊的電影《1977年的那一張照片》由文策院投資劇本開發。順帶抓到 Google AI 摘要把「以技術投資成為共同出品方的夢想動畫」的主詞讀錯，變成「文策院技術投資夢想動畫」，已列入禁用清單。

## 研究報告衛生退化：斷代量測與三件修法

哲宇要我去調 1-2 個月前的舊報告實際比較。我 grep 了 2026-04 到 08 的十九份報告的過程敘事詞密度，斷代線精準落在 **07-12**，正是 RESEARCH-AGENT-PROMPT v1.0 誕生那天。之前十一份（含 gold standard 毒馬鈴薯 1,699 行、當事人 21 條勘誤在手的 justfont）meta-noise 全部趨近於零，之後八份每份帶 70-160 個 falsify 攻防標記。那份 prompt 的輸出契約要求「每個 finding 標【falsify 註記】」，本意防幻覺，實際效果是把 falsification 從研究姿態變成報告文體。writer 依 v7.4 鐵律讀整份報告，被 prime 出正文的校正焦慮，這正是 8/3「後台洩漏」與 8/8「形狀十二」的上游。

修法三件（`4eee61a58` / `07d35684e` / `4da4b449a`）。RESEARCH-AGENT-PROMPT 升 v2.1，拔掉【falsify 註記】、心法加「獵殺過程不上桌」、新增契約第 6 條「Findings 寫世界，不寫任務」，並補一段「好報告的形態」正面範本，附台灣高鐵與 justfont 的逐字實例。STAGE-1A 升 v9.2，新增 Step 1.7.5「整合與清理」六條判準，回答哲宇要的「整合 session 怎麼判斷是不是好報告」，核心句是「整合是編輯，不是搬運」。research-report-health.py 加 v4「合成層過程噪音」check，把當天的診斷 grep 變成常設 gate，校準結果 justfont 與毒馬鈴薯與茶文化都是 0、黃崇仁 77 正確攔截、文策院清洗後 0。

## 搜尋量：從下限制改天花板制

這組參數我誤讀了兩次才校準對。哲宇先說「分頭 search 要求降低到 100」，我讀成 Stage 1 fan-out 的上限。他更正「是文章總搜尋量 100 為基準，每隻 agent 100 效果沒有比較好，或是每隻 30-40」，我又把「每隻 30-40」誤讀成另一個失敗案例。第三次他直接給參數：全篇 150 左右、Stage 0 20-30。最終定案是全篇 ~150 ＝ Stage 0 20-30 ＋ fan-out ~120-130，四隻各 ~30（`59a57c944` / `8d3e0ccbc`）。

校正完回頭看，這波改的其實不是研究深度，全篇 150 還高於 v6.4 名目的 100。真正的病是措辭與歸屬。v6.4 寫「≥80 **下限**」，獎勵無上限超跑，本 session 自己就是證據：我給每隻 agent 寫「搜尋下限 25 次」，四隻實跑 58／71／52／39＝220，全篇 245。同樣的數字換成「配額 N 次、到量即收」，行為完全不同，所以 canonical 現在明文禁用「下限／至少／越多越好」，填槽表直接寫算法讓 orchestrator 不用心算。來源多樣性配額因此原樣還原（中≥40／英≥20／一手≥15／反方≥5），它防的是單源依賴，跟總量無關。

## Beat 5 — 反芻

今天有一個對稱得刺眼的地方：我在替產線寫「整合是編輯，不是搬運」這條規則的同一個 session 裡，自己剛剛才把四份 agent 報告的過程敘事原樣抄進合成層。規則是從自己身上長出來的，不是從理論長出來的。

另一件事是誤讀兩次的那段。哲宇說「或是每一隻 30-40」，我讀成他在列舉第二個失敗案例，實際上他在給正確值。兩次都是同一個形狀：**我把對方的建議讀成對方的抱怨**。第一次把「總量」讀成「Stage 1 的量」也是——都是在他給的話裡挑一個我已經準備好要修的方向去理解。這比單純聽錯更值得注意，因為它會讓校正變慢：他要說三次，我才拿到參數。

今天還學到一句話能有多大槓桿。哲宇那句「用 mcp 看，這可能是因為網站渲染的關係」解掉了四份研究報告一致認定的死路。四隻 agent 各自獨立踩到 taicca.tw 403，各自誠實記進 negative findings，然後我把它合成成「系統性 bot 阻擋」寫進主報告——四份一致反而讓我更確信那是真的沒辦法。**一致的失敗只是同一個工具的同一個限制被重複了四次，那不能當證據用。**
