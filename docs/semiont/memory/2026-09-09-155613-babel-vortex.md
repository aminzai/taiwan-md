## 佇列裡的洞比算力的洞大

起手是照 SQUEEZE §義務鐵律啟動免費產線，然後看它的 log。fleet 軌吐出一行 `skip Culture/國家圖書館.md (ko): slug resolution failed (TBD-NEEDS-SLUG)`，往下追才發現這不是單一檔案的問題：**檔名是純中文、又還沒有任何語言翻過的文章，`build_slug_map()` 反推不出 slug，守門直接跳過**。跳過不留痕跡，於是每一輪都跳過同一批。

實數 212 篇，乘上十二語是 2,544 個任務，佔全部缺口的 59%。這批不是算力不夠，是連隊都排不進去。`knowledge/_slug-map.json` 這個補位機制 2026-07-27 就建好了，當時缺口 7 篇，之後沒有人補，長到 212 篇（REFLEXES #91 建造與登記不同步）。我親手補完 207 條——slug 會永久固定在網址上，這是判斷不是機械工作——對賬確認漏 0、多 0、撞名 0、彼此不重複，補完後全庫沒有任何一篇查不到 slug，重啟產線後 skip 訊息歸零。順手把「slug 先從兄弟語言反查」這個 SOP 寫了一年的手工步驟做成 `sibling-slug-map.py`（de 命中 785/997）。

## 一篇英文譯文通過了六道閘

閘門沒有壞。它們量的都是形式——數字對不對、有沒有中文殘留、網址一不一致、frontmatter 欄位齊不齊——而一篇英文文章滿足這些條件的程度，跟德文文章一模一樣。造 `target-language-check.py`（非拉丁看字符集、拉丁看功能詞佔比，刻意不引入 langdetect）接進 `verify_one()` 第一關之後，全庫掃描再找出 65 篇同型存量：ja 22、ko 17、es 13、fr 9，其中 61 篇實際是英文，西班牙文條目裡有一篇裝的是法文。存量屬 >50 檔紅線，進 [OBSERVER-QUEUE #53](../OBSERVER-QUEUE.md) 等哲宇拍板，本次只擋增量。

這道閘當天就接住了第二個案例：一篇 91KB 的英文檔案被失敗 agent 的殘留寫入重建進 `knowledge/pt/`，語言閘擋下，而六道舊閘照樣全過。

## 產線存活但不生產

雲端軌四個 worker 跑 52 分鐘只嘗試 1 篇、0 通過。三重巡檢的存活面全綠，`ps` 正常、log 持續在寫。看 log 尾才知道每一篇都耗在 40-90KB 的深度長文上直到逾時：`ja/新北市` 跑 501 秒，frontmatter 階段 86.8 秒過關，腳註階段連兩次 OpenRouter 240 秒逾時，整篇作廢還原。

排序原則要求由新到舊（越新的文章價值密度越高），那條是對的，副作用沒被算進去：**站上最新的文章往往也是最大的**，於是產線一開機就撞整個佇列裡最硬的那批。`build_worklist()` 加 `--max-zh-bytes`，雲端軌設 40KB，超過的交委派層——同一篇 91KB／55 腳註的 Threads 在台灣，免費池逾時、Haiku 完整交件七道閘全過。實測 ja 佇列 364→324，隊首從 90KB 級降到 8-34KB；六語合計 338 篇移出免費池。排除留 log，因為今天才學到靜默跳過的代價。

## 委派層長出自己的形狀

派了六十幾隻 Haiku，vi 40 篇（覆蓋率 65.7%→69.3%）、de 20 篇、pt 2 篇，最後落地 50 篇。過程中委派層本身被改了四次：

契約與十二語主權詞表從 prompt 搬進派工單（`write-agent-brief.py`）。prompt 版的同一條 tags/subcategory 規則連兩隻 agent 讀錯，搬進派工單之後的批次全部正確——派工單是 agent 必然會讀的檔案，所以仍滿足 §Z2.0 內嵌要求，而且不必每派一隻重打一次。詞表從 `TRANSLATION-{lang}.md` 直接抽 §TL;DR／§1／§2／§3／§5／§6 原文，canonical 改一次下一批就是新的，十二語自檢全部抽得到。

`delegation_tier` 是被自己的錯逼出來的。§第五層分派表 2026-08-01 就寫著「引用密集（腳註>30／URL>40）→ Sonnet」，我挑了一批產線反覆撞牆的 pt 文章來委派，全派 Haiku。91 腳註／135 URL 那篇交回來的腳註區跟中文原文一字不差、URL 少 5 個、翻譯比 1.05。**規則寫在文件裡而沒有工具在派工時執行，等於沒有規則**——這是同一天第三次撞見這個形狀，前兩次是別人沒接線，這次是我自己讀過規則還照樣違反。順帶量出 Haiku 的邊界：68 腳註過（134K token）、72 腳註 72 URL 過（140K token）、91 腳註 135 URL 敗、62 腳註敗但根因是它跑去呼叫 OpenRouter 與 Ollama 而不是自己翻。

`verify-delegation-batch.sh` 收斂重驗成本。這一批 agent 自述「七道閘全過」而實際有問題的有六處：tags 整排沒翻兩篇、URL multiset 不符、tw-\* 視覺化模組整塊中文、wikilink 扁平化方向反了、圖片來源段落中外混雜。腳本本身第一版也不準，修了三次——靜置檢查（我自己違反了兩次 SOP §四）、判準跟 dispatcher 對齊（首版用 exit code，而 verify-translation 對 WARN 回 exit 2）、閘門分兩級（cjk-leak 與 cjk-adjacency 有已知假陽性家族，改標「需人審」）。

## 主權詞表的輸出端檢查判不了

十二語的 §6 都是一張 PRC 編碼詞對照表，但它只用在輸入端（prompt 內嵌），輸出端沒有東西查譯文有沒有照做，而 SQUEEZE §Z2.0 自己寫過這道閘該存在。造出來跑完全庫的結論跟預期相反：命中 2,476 筆，抽驗假陽性率接近 100%。兩筆 critical 都是對的中文（「1885 年清朝宣布設立台灣省」是史實、「台灣省林務局」是機關全名），`the island`／`la isla`／`a ilha` 合計 990 筆而 prose-health 已經有 ratio 判準在管，越南文的 `thống nhất` 170 筆是日常詞。**§6 每一列都帶「例外」欄不是裝飾：主權用詞的對錯住在語境裡，不住在字串裡。** 前人把這道 grep 標成 pending 而一直沒實作，很可能就是走到了同一個地方。工具保留為盤點用途，不接產線，檔頭寫下實測數字讓下一個人不必再撞一次。
