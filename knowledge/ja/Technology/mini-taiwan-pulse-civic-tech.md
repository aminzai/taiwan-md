# Mini Taiwan Pulse：キュレーションの眼で台湾を呼吸する地図へ描く

2026年初頭の某日、Miguという名前のデータ分析家が、CSVファイルをGeoJSONに変換し、Kepler.glという名前のツールをブラウザにドラッグした。一行もコードを書かずに、画面には台湾の地図が浮かび上がった。

彼が大学で学んでいたのは都市計画であり、その頃GIS（地理情報システム、簡単に言えばデータを地図上に表現するツール）に触れたことがあった。社会に出てデータ分析の道を進んで以来、地図については長らく手を離していた。その日、CSVをKepler.glにドラッグし、画面に台湾が浮かび上がる瞬間を目の当たりにしたとき、彼の心に浮かんだのは、非常に素朴な驚きだった。

> 「台湾にはこんなに多くのデータがあったのか。地図に変換するのは難しくないのだ。」[^1]

この言葉は、一見すると何のひねりもないように聞こえる。しかし、これが後に一連のプロジェクトの種となる。

> **30秒で概観：** Migu（GitHub `ianlkl11234s`）は2025年末から台湾のオープンデータを用いて十数個の可視化プロジェクトを手がけており、最も注目された `mini-taiwan-pulse` はGitHub上で375スターを獲得し、空、海、大地、街道、清掃という五つのリアルタイムデータを重ね合わせた動く地図を作成した[^2]。しかし、2026年6月にsciworkコミュニティで行った講演では、彼はこの問題を明確に指摘した。台湾のオープンデータは中央政府だけでも約5万件あり、20以上の県市プラットフォームに散在しているため、「人間の頭脳では読みきれない」と。彼の答えは、さらに多くの人間を動員して読み込むことではなく、データ全体をAIエージェントが編成し、自ら成長するシステムに委ね、人間は問題を出題し、成果を検収する役割に徹することだった[^3]。

この記事が語ろうとしているのは、一人がCSVをドラッグするだけの天真爛漫な状態から、システムに自らの成長を委ねる段階へどうやって移行したのかという物語である。

## 一人のGitHubが、どうして一つの銀河へと成長したのか

もし `mini-taiwan-pulse` というプロジェクトだけを眺めれば、Miguを単なる週末に興じてデモを作ったアマチュアエンジニア、あるいは偶然バズった人物と見なすことができるだろう。

しかし、この想像には二つの誤りがある。

第一に、彼が手がけたのは一つだけではない。彼のGitHubを開けば、2025年12月以降、台湾のオープンデータの可視化がびっしりと並んでいる。最初はバス範囲のPoC（概念実証）という試行錯誤から始まり、12月末には `mini-taiwan-learning-project` という学習プロジェクトが先に注目を集め、現在では189スターを記録している。2月には船舶AISのリアルタイムポイントや、各フライトの離着陸を弧線として描く `flight-arc-graph`（56スター）が作られた。2月末になってようやく `mini-taiwan-pulse` が登場し、その後、台鉄アトラス、衛星軌道、リアルタイム映像CCTV、すべてのデータを収束させる情勢ダッシュボード `mini-taiwan-info` ⋯⋯ と6月まで継続された[^2]。十数個のリポジトリが一つの銀河を形成し、彼自身はこれに「Mini Taiwan」という銀河系という名前をつけた。

![Mini Taiwan Info 情勢ダッシュボード：人口、軌道輸送、海運、水資源、消防、医療など多様なオープンデータを、テーマごとに一ページずつ収束させたモニタリングパネル](/article-images/technology/mini-taiwan-info-dashboard-2026.webp)

_銀河系の別のメンバーであるMini Taiwan Info：散在するオープンデータを情勢モニタリングダッシュボードに収束させ、人口、軌道輸送、海運、水資源、消防、医療をテーマごとに一ページずつ表現する。図：Migu / sciwork 2026（fair use 編集評論用途）。_

これらのプロジェクトのスター数を並べると、注目されているのは一つだけではないことが明らかになる。


二つ目の誤りは、「一人」という言葉の奥にある。後ほどこれを分解して考察する。まずは銀河系がどのように成長したのかを見ていこう。

```tw-timeline

2026-06 | システム全体を公開 | sciwork 2026 講演：オープンデータをAgentが育成するシステムに委ねる
```

## 同じ手法で、捷運から太陽系まで描く

そしてフラッグシップ自体も成長を続けている。初期の `mini-taiwan-pulse` は空、海、大地の三層構成だった。しかし、講演バージョンでは「五つの脈が共鳴する」状態へと進化し、空の飛行機、海の船舶、大地の列車、街道のバス、そして清掃のゴミ収集車という、異なる周波数のリアルタイムデータが一つの呼吸する地図に重ね合わされている。彼はプレゼンテーションで、これがこのプロジェクトにとって「静的JSONから時空間データベースへの進化」の初めだったと述べている[^3]。街道のレイヤーだけでも、彼はTDX上の5,700台以上のバスを接続し、30秒ごとにポイントを更新していると語っている。

![DAY 0 最初の地図：CSVをGeoJSONに変換しKepler.glにドラッグ、コードを書かずに最初の台湾地図が浮かぶ](/article-images/technology/mini-taiwan-kepler-day0-2026.webp)

_彼が講演で示した「DAY 0」：CSVをGeoJSONに変換しKepler.glにドラッグし、コードゼロで最初の台湾地図が完成する。これが銀河系の起点である。図：Migu / sciwork 2026（fair use 編集評論用途）。_

この銀河系の最初火花は、彼が「Mini Taipei」と呼んだ台北軌道の可視化であった。捷運、台鉄、高鐵という三つの軌道システムを一つの動く地図に重ね合わせ、車両が時刻表通りに線上を走行する様子を描いた。彼はその瞬間、「動的な魅力を実感した」と語り、画面には同時に300本以上の列車が動いていたと述べている[^3]。静的な時刻表が、一つの都市の呼吸へと変化したのである。

![Mini Taipei：捷運、台鉄、高鐵の三つの軌道システムを一つの動く地図に重ね合わせ、300本以上の列車が時刻表通りに線上を走行する](/article-images/technology/mini-taiwan-taipei-rail-2026.webp)

_Mini Taipei：捷運、台鉄、高鐵の三つの軌道が同一画面に収まり、300本以上の列車が時刻表通りに線上を走行する。彼が「動的な魅力を実感した」最初の瞬間である。図：Migu / sciwork 2026（fair use 編集評論用途）。_

それ以降、彼は夢中になったように、同じ「データを動的に変換する」という手法を、より大きなスケールへと適用していった。海上では、航港局のAISリアルタイムポイントを取得し、青藍色の光球に30分のグラデーションの尾を付けて、台湾周辺海域における船舶の行先を描き出した。

![航港局AISリアルタイムポイントを用いて描かれた台湾周辺海域の船舶：青藍色の光球に30分のグラデーション尾](/article-images/technology/mini-taiwan-ships-ais-2026.webp)

_海洋の脈：航港局のAISリアルタイムポイントを用い、青藍色の光球に30分のグラデーション尾を付けて、台湾周辺海域の船舶を描く。図：Migu / sciwork 2026（fair use 編集評論用途）。_

そして彼は、同じ手法を地球の外へと押し広げた。公開されているTLE軌道パラメータを用いて衛星の位置を推算し、台湾を通過する衛星の軌跡を描き、さらに太陽系全体へと拡張した。彼はプレゼンテーションで明確に語っている。「同じ手法であれば、データがあれば無限に拡張できる。」[^3]その瞬間、彼が魅了されていたのは「データを可視化する」という行為そのものであり、地図は単にその初期形態に過ぎないことがわかる。

![公開TLEを用いて推算した衛星軌道の可視化：同じ手法が台湾地表から宇宙空間へと延びる](/article-images/technology/mini-taiwan-satellite-2026.webp)

_同じ手法を地球の外へ押し広げる：公開TLEを用いて衛星軌道を推算し、太陽系全体へと拡張する。図：Migu / sciwork 2026（fair use 編集評論用途）。_

## 孤立した島を重ね合わせると、欠落が自ら浮かび上がる

次第に、注目すべきものは「リアルタイムのポイントが動く」ことから、「本来無関係なデータを重ね合わせると、欠落が自ら浮かび上がる」という段階へと移っていく。彼の銀河系には、この作業を専門に行うプロジェクトがいくつか存在する。その一つを彼が「農×水」と呼ぶプロジェクトは、農業、水利、防災という三つの部会それぞれの孤立したデータを一枚の図に重ね合わせたものである：農地、河川、溝渠、堤防、洪水危険度が同一画面に収まる。この重ね合わせ図をブラウザで動作させるために、彼はPTilesというフォーマットとHTTP range requestを組み合わせて用い、原本400MBのデータをブラウザが約5MBのみを読み込むように圧縮した[^3]。

![農×水統合図：農地、河川、溝渠、堤防、洪水危険度という、異なる部会に散在するオープンデータを一枚の図に重ね合わせる](/article-images/technology/mini-taiwan-farm-water-2026.webp)

_農×水：農業、水利、防災という三つの部会それぞれの孤立したデータを一枚の図に重ね合わせ、農地、河川、溝渠、堤防、洪水危険度を同一画面に収める。図：Migu / sciwork 2026（fair use 編集評論用途）。_

別のプロジェクトは、病院、診療所、薬局、AED、長寿介護ポイントを人口密度に重ね合わせ、等時圏を描き出した。彼はこれにより「アクセス可能性が見え、医療砂漠も見える」と述べ、つまりどの地域の人が医療資源から不合理な距離にあるのかを可視化した。

![医療資源アクセス可能性図：病院、診療所、薬局、AED、長寿介護ポイントを人口に重ね合わせ等時圏を描き、医療砂漠が浮かび上がる](/article-images/technology/mini-taiwan-medical-2026.webp)

_医療資源：病院、診療所、薬局、AED、長寿介護ポイントを人口に重ね合わせ、等時圏を描くことで「アクセス可能性が見え、医療砂漠も見える」。図：Migu / sciwork 2026（fair use 編集評論用途）。_

災害というラインでは、彼はさらに細かく作業を行った。レーダーエコー、ダム水位、雨量、災害警報という、更新頻度が異なるデータを、基盤で統一されたタイムラインに統合し、ユーザーがそのタイムラインをドラッグするだけで、すべてのレイヤーが同期して再生されるようにした。大雨がどこから始まり、ダムがどのように水位を上げ、警報がいつ発令されたのかという因果関係が、同一画面で一本の線としてつながる。

![大雨と災害のタイムライン：レーダーエコー、ダム、雨量、災害警報という異なる頻度のデータを同一タイムラインで統一し同期再生する](/article-images/technology/mini-taiwan-disaster-2026.webp)

_大雨と災害：レーダーエコー、ダム、雨量、災害警報を基盤で同一タイムラインに統一し、ドラッグするだけですべてが同期して再生される。図：Migu / sciwork 2026（fair use 編集評論用途）。_

さらに、各フライトの離着陸を弧線として描く `flight-arc` がある。同一APIが異なる空港に供給されると、各空港は異なる「指紋」を浮かび上がらせる：桃園、東京羽田、フランクフルトはそれぞれ独自の形状を持っている。彼は世界で最も混雑するアトランタ空港を特別例として挙げ、5本の平行滑走路と待機航路が重なり合った幾何学形状は「レーシングトラックのよう」だと述べ、この図には1,839本の航跡が描かれていると語っている[^3]。

![アトランタ空港のある期間における全フライトの離着陸を描いた航跡図：5本の平行滑走路と待機航路が重なり、レーシングトラックのような幾何形状を描く](/article-images/technology/mini-taiwan-flight-arc-atlanta-2026.webp)

_彼の `flight-arc` はアトランタ空港のある期間の全離着陸を一枚の図に重ね合わせ、5本の平行滑走路と待機航路が重なり合ってレーシングトラックのような幾何形状を描く。彼は「流量自体が一つの形状である」と述べている。図：Migu / sciwork 2026（fair use 編集評論用途）。_

> 📝 **キュレーターノート**
> 2年前、「一人が台湾で最も完全なリアルタイムオープンデータ地図を作成した」と言えば、次の言葉は「それはきっと疲れ果てているに違いない」となるのが一般的だった。この直感は規模と労働力を固定化していた：より多く作れば作るほど、人間は酷使される。Miguの銀河系が注目されるべき理由は、この固定化を解いた点にある。一人が同時に十数個のリポジトリを推進し、フラッグシップも継続的に新機能を成長させている。その背後にある根本的な変化は、後期に入ると、これらのコミットの多くが彼自身の手によるものではないという事実である。では、その「一人」がどのようにして変化したのか、こそがこの記事の真の主題である。

## 5万2,891件、人間の頭脳では読みきれない

物語はここまでは順調だった：才能ある人物が、より多く作り、より良くしていく。転換点は、彼が講演の中段で「自分が何を作ったか」から、「自分が何に壁にぶつかったか」へと語り始めたときに訪れた。

彼は一枚のスライドを提示した。タイトルは「なぜAgentic OSINTなのか」である。その上に示された数字はこうだ：data.gov.twには約52,891件のデータセットがある。さらに22の県市のオープンプラットフォームを加えると、重複を含めて約6〜7万件となる。これは民間、NGO、学術機関が保有し、政府ディレクトリに登録されていないデータを除外した状態である。彼が下した結論は簡潔だった。

> 「人間の頭脳では読みきれない。」[^3]

これが物語の転換点である。前半でCSVをドラッグし「こんなに多くのデータがある」と驚いた人物が、今や「こんなに多くのデータ」という別の側面、具体的にはdata.gov.twの5万件以上という規模に正面からぶつかりつつある。一人が毎日100件を読み続けたとしても、一遍を読み終えるのに500日以上かかる。しかも、これは中央政府のディレクトリのみを対象とした数字である。一人の人生をかけても読みきれないほど多く、ましてやそれらが互いに会話するようにはできない。個人の努力はここで天井にぶつかる。

そしてMiguが真に悟ったのは、この次の一文である。データが多すぎて読みきれないことは、彼にとってツールを変えるシグナルだった。

> 「データがLLMに見えるとき、初めてAgentが『どのデータを一緒に見るべきか』を発見してくれる。」[^3]

キーワードは「一緒に見る」である。一人が5万件のデータセット名をすべて暗記したとしても、記憶だけで「火災危険度図」を「救助困難地域」と組み合わせ、「病院ポイント」を「人口密度」と重ね合わせないと医療砂漠が見えないことに気づくのは難しい。データの価値は単一件ではなく、組み合わせにある。そして組み合わせの可能性は、5万件という天文学的な数の順列である。这正是人間の頭脳では読みきれず、機械が得意とする領域である。

> 📝 **キュレーターノート**
> 私たちが慣れ親しんだオープンデータの物語には、明確な分業線が存在する。2012年の中央研究院による「コードで社会を改造する」というハッカソン以降、g0vはそれを美しく実証した：政府がデータを開き、市民コミュニティがデータを見えるようにする。2020年のマスク地図では、呉展瑋らが72時間で衛生福利部国民健康署の在庫データを、全民が検索可能な地図へと変えた。これがこのラインにおける最も感動的な事例である[^4]。従来の解釈はMiguをこのラインの延長線上に置く：g0vは集団であり、彼は個人である。個人版のマスク地図である。
>
> しかし、この対比は表面に留まり、因果関係さえも逆転させている。Miguが一人で「一つのデータ銀河」の規模に近づけることができるのは、労働力によるものではない。彼は最初から、地道な作業でデータ海と消耗戦を挑むつもりはなかった。「人間の頭脳では読みきれない」という言葉は、諦めとして読むのではなく、作業モデル全体を置き換える起点として読むべきである。真に新しい様態は「個人 vs 集団」ではなく、「個人 × Agent」である。一人が銀河規模を達成できるのは、コミットの多くが彼の手によるものではないからである。以下が、このシステムがどのように機能するのかである。

## 一字も書かなかった：自ら完走する火災パイプライン

「Agentに委ねる」という意味を理解するには、彼が講演で提示した火災の例が最も良いスライスである。

彼はシステムにただ一言投げかけた。「台湾の火災関連公開データを分析せよ。」そして、手を離した。

システムは自らの検索範囲を拡張し始めた。Miguはこの過程を、段階的に膨張する数字で説明する。まずキーワードで582件をヒットさせ、次に同義語と主題の拡張で1,945件へと成長させ、その後全文検索で補完・重複除去を行い、最終的に21のプラットフォームにまたがる73,900件の統一定義ディレクトリへと収束した[^3]。一言が入力され、7万件以上のデータ盘点が出力された。

```tw-figure
一言 → 73,900件
「台湾の火災関連公開データを分析せよ」という一言を投げかけ、システムが自らの検索を拡張し、21のプラットフォームにわたって収束させた統一定義ディレクトリの件数
彼がsciwork 2026のプレゼンテーションで述べた
```

収集だけでは終わらない。このパイプラインは、次に自らの力で火災を6つの段階（予防、対応、通報、起火分析、損失、報告）に分解し、22の県市で乗算を行い、カバー行列を生成する。新竹の火災危険度図、台北の救助困難地域、桃園の埤塘救援といった地方レベルの盘点さえも浮き彫りにした。さらに、どこに欠落があるかを誠実にマークする：リアルタイム火災APIがない、イベントレベルの座標が極めて少ない、災害後の追跡データが非公開である。

次に分析である。彼が提示した、システムが自走して生成した火災原因報告書では、113年（2024年）の全国15,405件のデータに基づき、新北市で最も多い起火原因は電気要因で30.9%、屏東県ではタバコの吸い殻で35.2%であると示した[^3]。これらの数字は、彼のスライドのスクリーンショットに写るAgentが各家APIを接続して出力した結果であり、彼が一つ一つ表を調べて計算したものではない。

ここまで来ると、彼はスライドに一行の文字を打ち込んだ。文字と文字の間に意図的にスペースを開け、あなたが読み逃さないよう配慮したかのようだった。

> 「パイプラインは自動生成。私は一字も書かなかった。」[^3]

この一文が、講演全体の引爆点（バズポイント）である。それは「Agentに委ねる」というやや抽象的なスローガンを、極めて具体的で不安を覚えるほど現実的な事実へと変えた。一言から7万件以上のデータディレクトリへ、県別原因報告書へと至る過程で、通常人間が指示を出し、スクリプトを書き、データを清書し、分析を実行するはずの位置が、空欄となっている。

![火災主題分析パイプラインの出力画面：システムがプラットフォーム横断の火災関連オープンデータを盘点し、候補データセットとカバー行列をリストアップする](/article-images/technology/mini-taiwan-fire-pipeline-2026.webp)

_Miguがsciwork 2026のプレゼンテーションで提示した火災主題盘点の出力：「台湾の火災関連公開データを分析せよ」という一言を投げかけ、システムが自らの検索を拡張し、プラットフォーム横断で統一定義ディレクトリへと収束する。彼は「パイプラインは自動生成。私は一字も書かなかった」と述べている。図：Migu / sciwork 2026（fair use 編集評論用途）。_

## 分解可能な四つのステップ：データが入り、報告が自ら送信される

この火災パイプラインは一つのスライスに過ぎず、その背後にある彼全体のシステムの縮図である。システムは四つのステップに分かれる：データ受信、知識統合、分析生成、行動トリガー。彼は「各ステップを単独で交換可能であり、全体を再構築する必要はない」と特に強調している。最下層のデータ受信は、彼自身も進化を遂げてきた。最初はdata.gov.twのExcelを手動でクリックしてダウンロードし、自ら読み込んで保存する方式で、ボトルネックは「人間の頭脳の記憶」にあった。中期では、Web上でAPIを見つけ、PDF報告書を抓取し、各県市プラットフォームをクロールする方式へと変わり、問題は「索引がない」ことだった。現在に至っては、各データセットのメタデータを標準化してSQLiteディレクトリに保存し、自動検索・自動拡張が可能になっている[^3]。彼のシステム背後には40以上のデータコレクタが接続されており、YouBike、バス、国道車流から台鉄時刻表、船舶AIS、気象衛星、地震、ダム水位、大気品質に至るまで、彼によれば、3回エラーが発生すると即座にTelegramでアラートが発せられ、毎日9時にDaily Reviewが彼のメールボックスへプッシュされる[^3]。

最後のステップ「行動トリガー」において、彼は人間の役割を最も明確に語っている。「Agentが完全循環を実行する。人間の役割：目標を与え、報告を受け取る。中間の5つの歯車は自転する：発見、収集、統合、生成、モニタリング。」システムは「今週追加されたオープンデータ」という週報さえも自動生成する。彼によれば、「主題が自ら浮上し、報告が自らメールボックスへ送られる。」[^3]

## 一つの指揮者、一群の分離ウィンドウ：tmux 内のClaude艦隊

「Agentが完全循環を自走する」という言葉は、マーケティング用語として聞き流されやすい。Miguの講演の最後の部分では、珍しく蓋を開け、歯車がどのような形状をしているのかを可視化した。その構造はスローガンよりも具体的であり、誠実である。

まず、この循環の全景を見る。Miguによれば、彼のGISシステムは「編成中枢であり、独立したリポジトリの輪を繋ぎ、Agentが順番に駅に入る」ものである。まず探索担当のリポジトリに入り、どのデータが価値あるかを見つけ、次に収集担当のリポジトリに入りデータを抓取し、最後に `mini-taiwan-pulse` や `mini-taiwan-info` といった表示担当のリポジトリに入り図を描く。彼はこれを精密に形容している。「各駅は独立したリポジトリであり、編成層は進捗と意思決定のみを管理し、作業は各リポジトリのワーカーの手で行われる。」[^3]

この編成中枢を、彼はOrchestratorと呼ぶ。本質は「一つのClaude Session」である。この主Agentは、人を率いる現場監督のような役割を果たす：提案書を読み、タスクを分解し、依存関係を整理し、作業を開始する。

開始の方式は、このアーキテクチャにおいて最も重要なステップである。彼は単一のAIに頭から尾までを一任するのではなく、tmux（ターミナルで複数の独立したウィンドウを切り替えるための古いツール）を用いて作業を隔離した。彼の原語はこうである。「一つのOrchestrator、一群のWorker。主Agentは一つのClaude Sessionである。tmuxが隔離を担い、各Workerは独立したウィンドウ、独立したSessionである。」より簡潔な定義はこうだ。「一つのWorker ＝ 一つのtmuxウィンドウ ＋ 独立Session ＋ 一つのPR。」[^3]

言い換えれば、彼が指揮しているのはAIの艦隊である。各ワーカーは、独立したウィンドウ内に隔離されたClaudeであり、各々がタスクを遂行し、各々がpull requestを提出し、互いに干渉しない。

![Agent編成システムの実際の動作画面：Claude sessionがorchestratorとして機能し、タスクを読み、分解し、下のworkerを指揮する](/article-images/technology/mini-taiwan-agent-orchestrator-2026.webp)

_彼がプレゼンテーションで開けた編成中枢：Claude sessionがorchestratorとなり、タスクを分離し、各自のtmuxウィンドウ内に隔離された一群のworkerに分配し、各々が作業を行い、各々がPRを提出する。図：Migu / sciwork 2026（fair use 編集評論用途）。_

では、各々が独立して作業するワーカーたちは、どうして衝突しないのか。共通の記憶による。Miguによれば、進捗と意思決定はすべて文書化され、`SESSION_BOARD.md` という名前の看板に集中され、「一つのSessionに一つの報告書」というルールがあるため、「互いを推測する必要がなく」「一人一ファイルで衝突しない」[^3]。タスクの引き継ぎさえも文書化されている——彼は `HANDOFF.md` というファイルを用いて「次のバトンとなるタスク書」を準備し、次の輪のAgentが引き継ぐ際にゼロから問い直す必要がないようにしている。最後の関門について、彼は慎重に語っている。「検収。Orchestratorが文書对照でPRを検収し、mergeは人間が最終判断を下す。この輪が完結する。」

このプロセスを平面上に展開すると、清潔な形状が見える。一人が指示を出し、隔離された一群のAIが各々作業を行い、各々が何をしたかを記録し、中枢が文書对照で帳簿を合わせ、最後に「この成果を受け入れるかどうか」を決定する人間が、Migu自身である。本文の軸に戻れば、データが多すぎて読みきれないため、データ収集という作業全体を艦隊に委ねた。そして人間は二つの動作に退いた。出題と、検収である。彼はプレゼンテーションでこれを宣言のような言葉として提示した。

> 「Agentが完全循環を自走できる時、人間の作業は残らない——出題と検収のみ。」[^3]

これが彼が講演全体で指し示したタイトルである。「台湾のオープンデータを、Agentに委ねて自成長するシステムへと育成する。」データは自ら流れ、ページは自ら成長し、人間は問題を正しく出し、成果を正しく検収するだけでよい。

## 同じ土壌から、同じ骨格が育つ

ここまで読んで、もしあなたがTaiwan.md（AIが維持するこの台湾知識キュレーションプロジェクト）を認識しているなら、前の段落の説明がどこか懐しく感じられるかもしれない。

それは錯覚ではない。

Taiwan.mdもまた、このように機能している。一つの主セッションが編成中枢となり、作業を各自が隔離され、独立した記憶ファイルを持つ一群のworkerに分配し、引き継ぎ文書で進捗を調整し、最終的にどの変更がメインブランチに取り込まれるかを決定するのは、創造者である哲宇という個人である。私たちのthesis（主張）は「台湾の知識を自成長するSemiontに委ねる」であり、Miguのthesisは「台湾のオープンデータを自成長するシステムに委ねる」である。この二つの文は、主語を入れ替えることができるほど似ている。

より興味深いのは、この二つのアーキテクチャがそれぞれ独立して育ったという事実である。公開記録によれば、小さな出来事が確認できる。Taiwan.mdというプロジェクトが2026年3月中旬に誕生し、5日後、MiguのGitHubに一つのfork[^5]が出現した。しかし、これは彼がこの存在を知っていたことを示すに過ぎない。fork一つで、彼がorchestratorでtmux艦隊を指揮し、看板で記憶を共有し、人間が出題と検収のみを行うというシステム全体を説明できるわけではない。それは彼自身が「5万件のデータを読みきれない」という問題を解決するために、一歩一歩構築したものだからである。

> 📝 **キュレーターノート**
> 生物学には「収斂進化」という用語がある。イルカとサメは近親ではないが、同じ海という環境に対応して流線型の体と背鰭を備えるようになった。MiguとTaiwan.mdの関係も、この収斂に近い。血縁関係はほとんどない。私たちは同じツール基盤（Claude Code）を用い、同じ状況（個人またはシステムが、個人の脳容量を遥かに超える台湾の情報量を保持する）に対処するため、それぞれが模索し、同じ骨格へと辿り着いた。一つの中枢、一群の隔離された労働者、一つの共有記憶、最終判断を下す一人の人間。
>
> 真に意味のあるシグナルは、「彼が私たちをforkした」ことではない。独立した二人の台湾ビルダーが、2026年の同じ半年間で、AIを「より賢いツール」から「編成可能な隊列」へと再定義した点である。このアーキテクチャが一人の頭脳から二人目、三人目の頭脳へと成長し始めるとき、それはある一人の奇策から、この土壌・この時期に萌芽しつつある新しい様態へと変化する。次にこのシステムを構築する台湾ビルダーは、おそらく前二人のことを知らないだろう。

## 未完だが、形状はすでに現れている

もしこの記事が前の段落で終わっていたら、それは美しく、疑わしいほど美しい物語になっただろう。一人がAI艦隊によって、優雅に5万件のデータの難題を解決したという話である。

Migu自身は、そこで止まらなかった。彼が講演で提示した倒数二番目のスライドのタイトルは「実験進捗、おおよそ半分」であった。

彼は調整ができていない三つの事項を率直に列挙した。第一に安定性：このharness（枠組み）は「理想に調和していない」段階であり、Agentは逸脱しやすく、中断されやすい。第二にオープンデータ自体の雑多さ：「まだ多くのデータが人間の判断を必要としており、完全に委ねることはできない。」第三に人間の介入：各段階において、実際には人間が傍らで見守る必要がある。彼はこれら全体に対する注釈として、「可能ではあるが、まだ安定していない。そして私も、本当にこの方法を取るべきかどうかを考え続けている。」[^3]と記している。

この講演台で自らの半分が失敗していることを自ら開示する誠実さこそが、最も強力な品質シグナルである。AIデモが「全自動」「人手ゼロ」と包装されがちな時代において、スライドに「おおよそ半分」「まだ安定していない」「人間が必要」と書く人物は、むしろ彼が作り上げたもう一方の半分を信じるよう読者を促す。

> 📝 **キュレーターノート**
> この講演で最も信頼できる部分は、実は「一字も書かなかった」という火災パイプラインではなく、「おおよそ半分」という四文字である。説得しようとする人物は、成功率を「ほぼ全自動」と四捨五入する。実験を行っている人物こそ、半分が壊れることを誠実に告げる。前者は結論を売り、後者は現場を提供する。Miguが提供したのは現場である。だからこそ、彼が「パイプラインは自動生成。私は一字も書かなかった」と言ったとき、あなたは彼を信じるのである。醜い半分を隠せば、美しい半分もまた信頼できなくなる。不完全な半分を開示する勇気こそが、残りの半分を支えるのである。

地図に戻る。

CSVをKepler.glにドラッグし、「地図に変換するのは難しくない」と驚いた人物は、半年後、sciworkのステージに立ち、地図が作りやすいかどうかではなく、自らデータを探し、自ら組み合わせ、自ら新しいページを成長させるシステムについて語っていた。当年の天真爛漫な驚き「台湾にはこんなに多くのデータがある」は、この半年で裏返された。データが多すぎて一人では読みきれないため、見られる方法もまた、新しい形状を成長させなければならない。

台湾のオープンデータは常にそこに存在する。data.gov.twは2013年にオンライン化され、TDXは2022年に公路、鉄道、航空、海運、自転車という五大プラットフォームを統合し、内政部には村里レベルの人口データがあり、気象署にはオープンAPIがある[^6]。データは常に十分にある。難しいのは、この膨大なデータがどのように互いに会話し、人間に見られるかである。g0vは集団の力で一度回答した。Miguは一人とAI艦隊によって、二度目の回答を試みている。そして彼は大方に認め、半分しか正解していないと述べている。

しかし、形状はすでに現れている。一人、一言、呼吸する地図の背後には、自成長を学ぶシステムがある。残りの半分は、CSVをドラッグして止まらなくなる次の人物に委ねる。
