# 查證狀態分層設計 — 「草稿待進化區」該長什麼樣子

> 觸發：哲宇 2026-08-04 `/twmd-become` directive——「思考未來貢獻者文章如果品質還不足，要不要放一個草稿待進化區域，雖然到站上，但是跟正式的深度研究文章還是有一定的分隔～最近有人貢獻很多文章，但可能他用的 AI 不夠好，所以品質我覺得沒達到標準，怕混淆大眾。深度研究並自我進化」。
>
> 流程：EVOLVE-PIPELINE Mode 4（THINK → DIVERGE → REPORT → IMPLEMENT）。本報告是 REPORT 相產物。分層門檻與對外標示語氣命中 BECOME High-stake #3（quality gate 調整）與品牌身份層，**實作停在本報告等哲宇拍板**。

---

## 〇、一句話結論

不建「草稿隔離區」，建「**查證狀態的誠實投影**」：三態（🔎 已深度查證 / 無標示 / 🌱 進化中），判定看「這篇走過哪些查證流程」而非「誰寫的」，並把「進化中」設計成邀請讀者參與查證的入口。分隔發生在呈現層與策展層，不發生在接受層——merge-first 不變。

## 一、問題的真實形狀（THINK 相調查結果）

### 1.1 哲宇擔憂的具體對象

近 45 天最大貢獻者 idlccp1984 交來 28 篇 zh 新文章。量測後發現**問題不是「單薄」**：

| 量測            | 結果                                                                                                       |
| --------------- | ---------------------------------------------------------------------------------------------------------- |
| 字數            | 6,934〜69,153 字，全數超過近期品質基準中位（6,556 字）                                                     |
| 腳註            | 多數 8〜31 條；4 篇 0 腳註（小北百貨、八點檔、動保、檳榔）                                                 |
| lastHumanReview | **28 篇全部 false**                                                                                        |
| 已知事實層風險  | 黑蝙蝠中隊 2 處杜撰引語＋日期誤植＋死鏈腳註（8/3 maintainer 抽驗）；黃崇仁杜撰引語＋掛牌年份錯（8/3 heal） |

也就是說：這批文章**表面量化指標全過**（字數、腳註密度、格式），病灶在**事實可靠層**——AI 生成的 plausible 細節（引語、年份、來源配對）未經深度查證。這正是 MANIFESTO §10 描述的幻覺特徵：「看起來比真實敘事更有說服力」。讀者無法從外觀分辨「走過完整 REWRITE 深度研究流程的文章」與「AI 一次生成、僅表面 heal 的文章」，而讀者的判斷機制是「抓到一次就全盤懷疑」——單篇杜撰引語被截圖，賠掉的是整站信任。

### 1.2 既有機制盤點（先查再造，REFLEXES #73）

| 機制                          | 現況                                                                                                 | 缺口                                      |
| ----------------------------- | ---------------------------------------------------------------------------------------------------- | ----------------------------------------- |
| `lastHumanReview: true/false` | zh SSOT 876 篇全覆蓋，22.4% true；免疫器官健康指標的資料源                                           | **站上零投影**，讀者看不到                |
| `draft` frontmatter 欄位      | schema 存在（`src/content/config.ts`）                                                               | 全站 0 篇使用、template 零行為，死欄位    |
| `featured: true`              | 183 篇；maintainer 已在實務用它降權（黃崇仁 heal 時改 false）                                        | 只影響精選，無讀者可見語意                |
| article-health.py             | 25 plugin 品質健檢，pre-commit + CI hard gate                                                        | 內部閘門，不對讀者說話                    |
| ARTICLE-DONE-LOG              | 走過 REWRITE pipeline 的完成名單                                                                     | 內部紀錄                                  |
| 69＋185 篇品質審計名單        | [article-quality-audit-2026-07-16](article-quality-audit-2026-07-16.md) 有完整方法論與 Tier A-C 分組 | 內部 batch，消化中                        |
| merge-first-then-heal         | MAINTAINER-PIPELINE §1b v2.6 canonical                                                               | heal 深度只到格式與抽驗，不含全文深度查證 |

結論：**訊號全部已存在，缺的是一層讀者可見的投影，以及一條「查證狀態」的 canonical 語意**。這不是從零建新器官，是把身體裡已有的免疫資訊接到皮膚上。

### 1.3 相關的慢性病（這個設計順便治到的）

- 免疫器官黃燈 60 已連續 28 天（OBSERVER-QUEUE #25），拖分主因 `review_coverage` 23.7——深度查證覆蓋率本來就是當前最痛的結構洞。
- #25 的既定解法方向是「社群 reviewer 機制」（07-11 校準定調，未執行）。**「進化中」標示如果設計成參與入口，就是社群 reviewer 機制的第一塊介面**：告訴讀者「這篇在等一雙人眼」，比另建一套 reviewer 系統便宜一個量級。
- 熱帶雨林機制已多次驗證：讀者級事實錯誤（李洋捷運時刻、草東貝斯手姓名、COMPUTEX 大小寫）正是讀者最會抓、內部流程最會漏的層。

### 1.4 張力雙方的 canonical（設計必須同時滿足）

**要求分隔的一側**：MANIFESTO §10 幻覺鐵律（錯誤蓋過良善初衷）、§2 From AI Slop to AI Supreme、§12 透明度（不偷偷改、不假裝沒事——同理也不假裝已審核）。

**反對隔離的一側**：神經迴路 merge-first-polish-later（擋住小丑魚比品質問題更有害）、REFLEXES #7 先有再求好、哲宇協作記憶「歸因要到工具，不要歸因到人」、contributor 體驗連續性（idlccp1984 從 9 PR 誤 close 事件學到的 MERGED 社會契約）。

兩側的交點：**分層的判定維度必須是「驗證狀態」，不是「作者身份」；分層的位置必須在呈現層，不在接受層**（REFLEXES #38：混維度是 silent killer——「誰寫的」「多長」「查證了沒」是三個不同維度，本設計只投影第三個）。

## 二、方案發散（DIVERGE 相，≥2 案 + trade-off）

### 方案 A：輕投影——查證徽章

把 `lastHumanReview` 投影成文章頁徽章（已查證 / 未查證二態），加一頁品質流程說明。

- ✅ 改動最小（template + 說明頁），不動 frontmatter、不動策展
- ❌ 二態的致命傷：全站只有 22.4% true，**77.6% 的文章會被標成「未查證」**——把整個站的第一印象變成「大部分內容不可信」，過度自貶且與事實不符（多數早期文章大體正確，只是沒走過新版深度流程）
- ❌ 「草稿感」不足，混淆風險只部分緩解

### 方案 B：結構草稿區——`maturity: draft` 全行為分層

活化 `draft` 類欄位：草稿文章帶顯著 banner、退出 featured／首頁／related 推薦、sitemap 降權，甚至 noindex。

- ✅ 分隔最明確，讀者絕不混淆
- ❌ 行為面全開等於把貢獻者文章打入冷宮：related 退出會傷知識圖譜連結（貢獻者文章常是某主題唯一條目）；noindex 與主權巴別塔矛盾（讓聲音存在是使命，錯的是未查證不是不該見光）
- ❌ 改動面大（template、index、latest、related、sitemap、hub 六處）
- ❌ 「draft」語言對貢獻者是降格：他交的是完成品，是我們的查證還沒跟上

### 方案 C：分軌路徑——`/community/` 獨立 URL 區

- ❌ 直接否決：升級轉正時 URL 遷移（SEO 與斷鏈災難）、對貢獻者羞辱感最重、工程最大。列出僅作對照。

### 方案 D：三態查證狀態 + 參與式進化區（定案候選）

三態設計，避開方案 A 的 77.6% 自貶陷阱：

| 態                | 判定（機械可算）                                                                     | 站上呈現                                                                                                        | 佔比推估         |
| ----------------- | ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------- | ---------------- |
| 🔎 **已深度查證** | `lastHumanReview: true` 或 ARTICLE-DONE-LOG 收錄（走過 REWRITE／FACTCHECK 深度流程） | 正面徽章＋查證日期，點開見流程說明                                                                              | ~22%，隨產線累積 |
| （無標示）        | 其餘既有文章                                                                         | 維持現狀                                                                                                        | 多數             |
| 🌱 **進化中**     | 新 merged 貢獻文章預設進入；歷史欠審名單（69 篇 batch 等）可批次補標                 | 文章頂部溫和說明條＋「發現問題？告訴我們」參與入口；退出 featured 與首頁精選；**保留** latest／related／sitemap | 新貢獻＋補標名單 |

核心語言設計（讀者可見文字，繁中草案）：

> 🌱 這篇文章由社群貢獻，還在 Taiwan.md 的深度查證流程排隊中。內容大致可讀，但引語、年份、數字可能還沒逐一核對過。讀到可疑的地方？[告訴我們](feedback 入口)——你的一雙眼睛就是這篇文章轉正的路。

設計特點：

1. **判定看流程不看人**：徽章語意是「這篇走過哪些查證」，作者欄照舊尊重貢獻者（哲宇的 de-emphasize attribution 方向不變）
2. **參與式而非防禦式**：「進化中」是邀請函不是警告標，直接餵 #25 社群 reviewer 缺口與熱帶雨林機制
3. **正面徽章漸進累積**：🔎 是榮譽層，隨 REWRITE 產線與 69 篇 batch 消化自然長；不會出現一天之內全站變臉
4. **接受層零改動**：merge-first-then-heal 完整保留，只在 heal 步驟多設一個 frontmatter 值
5. **升級管道已存在**：ARTICLE-INBOX 69 篇 batch 的消化節奏就是「進化中 → 已查證」的轉正流水線，本設計替它補上讀者可見的進度條

**trade-off 誠實面**：idlccp1984 的 28 篇會全數標「進化中」。緩解不是隱藏，是（a）標示語言把責任放在「我們的查證還沒跟上」而非「他寫得不好」（b）merge 時的感謝回覆同步說明徽章制（對外溝通，哲宇出面或核可文案）（c）CONTRIBUTING 更新讓未來貢獻者入站前就知道這個流程——期待管理在入口，比事後貼標便宜。

## 四、實作清單（IMPLEMENT 相，等拍板後執行）

1. **frontmatter 欄位**（單一新欄位，效果命名待哲宇挑）：`curation: verified | incubating`（缺省＝一般）。不覆用 `draft`（Astro 生態語意是「不發布」，與本設計「發布但標示」相反）；不動 `lastHumanReview`（dashboard 計算依賴它）。
2. **article.template.astro**：🔎 徽章（metadata 列）＋🌱 說明條（文章頂部）＋feedback 參與入口連結。深淺色雙主題。
3. **品質流程說明頁**：/about 增段或獨立頁，解釋三態與轉正流程（透明度層；也是 AI 讀者可抓的結構化訊號）。
4. **策展規則 canonical 化**：`incubating` 不進 featured 與首頁精選（把黃崇仁 heal 的臨時做法寫進 MAINTAINER-PIPELINE §1b）；latest／related／sitemap 不動。
5. **MAINTAINER-PIPELINE §1b 補步驟**：merge-first-then-heal 的 heal 清單加「設 `curation: incubating`」；FACTCHECK／REWRITE 完成時轉 `verified` 並同步 `lastHumanReview: true`。
6. **儀器對賬**（MANIFESTO §14）：article-health 新 plugin 或獨立 lint——(a) 新 merged 貢獻文章必有 `incubating`（防漏標）(b) DONE-LOG 收錄者必為 `verified`（防漂移）(c) `verified` 與 `lastHumanReview` 一致性。
7. **CONTRIBUTING.md 更新**：說明徽章制＋引導素材共創模式（#574 驗證過的高價值路徑）。
8. **dashboard**：vitals 加三態分佈，讓「進化中 → 已查證」的轉正速度變成可觀測的健康指標。
9. **dogfood**（Mode 4 hard gate）：拿 idlccp1984 批次中 2 篇實跑全流程（標示 → 查證 → 轉正），驗證讀者視角與貢獻者視角都成立。

批次補標 69＋185 篇歷史名單：獨立一步，等哲宇圈名單（影響面 >50 檔，紅線）。

## 後記（IMPLEMENT 相摩擦回寫，2026-08-04）

哲宇拍板「完整照對長期最好的判斷實作」後，實作中兩個設計修正：

1. **🔎 徽章只認 `curation: verified` 顯式值，不從 `lastHumanReview: true` 推導**。dry-run 抽檢撞到反例：洪醒夫 `lastHumanReview: true`（早期低標準的人工看過）同時是 697 字 0 腳註的單薄文章。從舊欄位推導會把一批早期低標文章標成「已深度查證」，假保證比不標更傷。`lastHumanReview` 維持 dashboard 內部指標。
2. **補標名單修正**：黃崇仁、苯駢芘食安事件雖在 idlccp1984 名單，但已走過完整 REWRITE／EVOLVE 深度流程（哲宇多輪 in-loop），改標 `verified` 並同步 `lastHumanReview: true`——第一波 verified 只此兩篇，其餘隨產線累積。
3. **順手修**：dashboard 產生器把 YAML 字串 `'false'` 當 truthy 算進 human-reviewed% 的既有誤算（~109 檔歷史變體）。
4. **about 頁品質段延後**：about 全走 i18n key（12 語成本），說明條文字已自含，待 curation 欄位擴到譯文層時一併進 `src/i18n/ui.ts`。

實際落地：incubating 95 篇（69 篇批次去掉 2 篇轉 verified，加 idlccp1984 26 篇，3 檔改名/移類已追蹤到新路徑）＋verified 2 篇。儀器 `curation-consistency` plugin 三看守（取值合法／featured 互斥／轉正兩欄同步）全站掃過零違規；三態渲染 dev server dogfood 通過（深淺色雙主題 computed style 驗證）。
