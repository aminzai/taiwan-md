# 編輯室對抗 — 投影後／正文後 乾淨 context 審稿結構

> 2026-07-15 · 規劃稿（未升 pipeline canonical）  
> 觸發：哲宇「用 subagent 做編輯室對抗是結構的」+ 與陳睨對話（編輯台蓋回來、主編手、數位足跡／一手資料、社群爬文擋得兇）  
> 對齊：REWRITE v8.0 Step 2.0 投影 · Stage 3.6 成品總驗 · REFLEXES #31 / #42 / #75 / #77 · PROJECTION.md

---

## 0. 一句話

**在「投影藍圖」與「正文成品」兩道關口，各插一間乾淨 context 的編輯室：角色分席、任務互斥、裁決有主編，不准同一顆腦又寫又審。**

這不是 UI 上的彈幕或滑動留言牆（睨那邊的產品感）；是**產線上的編輯台**——把「總編輯看完整桌材料、質疑、要改寫」變成可重跑的 subagent 結構。

---

## 1. 現況地圖：已有什麼、缺哪一刀

```text
研究 fan-out → 合成 report → Step 2.0 投影（主 session 自寫）→ 派寫手 → Stage 3 草稿驗 → 3.6 成品總驗
                         ▲ 缺：投影無人審                          ▲ 有：原子 fan-out
                         ▲ 缺：編輯論點／骨架對抗                    ▲ 偏：事實 atom，少結構論證
```

| 已有                                                 | 仍缺                                                     |
| ---------------------------------------------------- | -------------------------------------------------------- |
| Step 2.0 投影藍圖 + 5 題 gate（人眼）                | 投影寫完後**乾淨 agent** 對抗審查                        |
| Stage 2 fresh writer（隔離舊文）                     | 正文寫完後**同一套編輯室**再跑一輪（不只 3.6 事實 atom） |
| Stage 3.6 verifier fan-out（引語／gloss／footnote）  | **論點／骨架／面向巡禮／炎上 spine** 的角色化審稿        |
| 研究：新聞／部落格／論文／podcast 檢索（非 FB 主爬） | 編輯室報告的 SSOT 落檔 + 回修 loop 儀器化                |
| persona gap-audit（20 路讀者）                       | 編輯室角色 ≠ 讀者 persona（見 §3）                       |

**病根（與投影同源）**：投影目前是 orchestrator 自產自驗。同一 context 容易「我剛寫的骨架當然過 shuffle test」。陳睨說的「編輯台蓋回來」＝需要**另一雙沒寫過藍圖的手**。

## 2. 與陳睨對話的對齊（產品邊界）

| 睨側意象                    | Taiwan.md 落地                                                                                                |
| --------------------------- | ------------------------------------------------------------------------------------------------------------- |
| 滑動時冒出社群留言          | **不做主路徑**：臉書／Threads 爬文擋得兇；不把彈幕 UI 當 ship gate                                            |
| 數位足跡才寫得出文章        | **研究 report 是編輯室唯一材料桌**（+ 必要時一手原件 URL）；禁止憑記憶發明「讀者留言」                        |
| 新聞／部落格／論文／podcast | 已是 RESEARCH 主戰場；編輯室可要求「某 claim 缺這類足跡 → 退回補研」                                          |
| 主編這隻手很有趣            | **Orchestrator = 主編**：收各席 critique、拍板改／不改、寫裁決，不自己再寫一版對抗意見                        |
| 思考泡泡而非傳統彈幕        | 產物是 **編輯室報告**（分席意見 + 共識／歧見 + 必改清單），可選前端之後再做「思考泡泡」展示，**不綁死本設計** |

**鐵律**：編輯室對抗的輸入是 **report + projection 或 正文**，不是模擬社群情緒。情緒／炎上風險用 spine 類型 + MANIFESTO 立體地愛 + 政治中立規則判斷，不用假留言。

## 3. 編輯室編制（角色 = subagent，乾淨 context）

每席 **1 agent = 1 角色**，平行 spawn（REFLEXES #42），**禁止 sequential 同一 agent 換帽子**。

### 3.1 投影編輯室（Step 2.0 之後、派寫手之前）— **HARD for depth**

輸入（唯讀）：

- `reports/research/.../{slug}.md` 合成報告（§6 fact-pack + 論點相關 raw）
- `reports/article-projection/{slug}.md` 投影藍圖
- 短 brief：spine 類型、題目、禁區（政治中立／立體群像等）

**不給**：舊文全文、orchestrator 寫藍圖時的閒聊、writer prompt 草稿。

| 席位                                | 模型建議         | 任務（只做這一件）                                | 必答問題                                                  |
| ----------------------------------- | ---------------- | ------------------------------------------------- | --------------------------------------------------------- |
| **主編（Orchestrator）**            | 主 session Opus  | 收件、裁決、回修指令；**不寫對抗文**              | 哪些必改、哪些 defer                                      |
| **結構主編**                        | Opus 或強 Sonnet | 論點／骨架／shuffle／全局功能                     | 論點是摘要還是主張？打亂 section 還通嗎？哪段是面向巡禮？ |
| **減法主編**                        | Sonnet           | 密度／CV 感／該砍未砍                             | 減法表是否誠實？哪三段可併？                              |
| **炎上／倫理席**                    | Sonnet           | spine × 立體地愛 × 政治邊界                       | 是否 contrarian 炎上？是否把受敬重對象寫成反例脊椎？      |
| **讀者席（可選，與 persona 合流）** | Sonnet           | 1–2 個高風險 persona 只問「讀完藍圖還想知道什麼」 | 資訊缺口 vs 結構問題分流                                  |
| **反方席（條件）**                  | Sonnet           | 僅矛盾驅動／政策辯論題                            | 最強反論是什麼？藍圖有沒有預留誠實 facet？                |

**產出**：`reports/editorial-room/{slug}-projection-review.md`

```markdown
# 編輯室報告 — 投影 — {slug}

## 各席 verdict（pass / revise / block）

## 必改清單（≤ 7 條，可執行）

## 建議但不擋 ship（≤ 5 條）

## 歧見（主編裁決）

## 回修：投影藍圖 diff 指令（給 orchestrator）
```

**Gate**：

- 任一席 **block** → 必須回修投影，再跑一輪（最多 2 輪，第 3 輪升級觀察者）
- 僅 **revise** → 主編勾選採納項，修藍圖後 **spot-check**（可不再全席，見 §5 成本）
- 全 **pass** → 才准派寫手

### 3.2 正文編輯室（Stage 2.5 覆蓋前／Fresh ship 前）— **與 3.6 分工**

輸入（唯讀）：

- staging 正文 `reports/article-evolve/{slug}.md` 或 draft
- **同一份**投影藍圖（寫手應執行的規格）
- research report（查證用）

| 席位                          | 任務                                                   | 與 3.6 的關係      |
| ----------------------------- | ------------------------------------------------------ | ------------------ |
| **結構主編**                  | 正文是否**執行**了藍圖全局功能？有沒有寫歪成面向巡禮？ | 3.6 不查這個       |
| **論點兌現席**                | 論點是否在中段被證明／被複雜化，而非頭尾各喊一次？     | 3.6 不查這個       |
| **聲音／節制席**              | 對位句型、破折號、晶晶體、校正焦慮、briefing 腔        | 補 prose-health    |
| **事實席（可 = 3.6.1 合併）** | atom falsify fan-out                                   | **就是**現有 3.6.1 |
| **順稿席（可 = 3.6.2）**      | 呼吸、機械自述、framing 殘渣                           | 現有 3.6.2         |

**原則**：**正文編輯室 = 結構／論點對抗 + 既有 3.6 事實三關**，同一「編輯室」名義、兩種任務包，避免造第三套平行 pipeline。

```text
正文寫完
  ├─ 包 A：結構編輯室（結構主編 + 論點兌現 + 可選炎上）  ← 新
  └─ 包 B：成品總驗 3.6（原子 / 順稿 / 視覺）          ← 既有
主編合併兩包 → 必改清單 → heal 後才 ship
```

**產出**：`reports/editorial-room/{slug}-prose-review.md`（可 link 到 research §audit）

## 4. 深度研究寫 report（編輯室上游）

編輯室**不替代研究**；它審計「桌上材料夠不夠撐藍圖／正文」。

### 4.1 足跡契約（給研究 agent + 編輯室共用）

| 允許／鼓勵                                                 | 不預設／明確不做                            |
| ---------------------------------------------------------- | ------------------------------------------- |
| 新聞、深度專題、官方／法規、學術、podcast 逐字稿、公開演講 | FB／IG 主牆爬取、假造社群留言當「社會情緒」 |
| 一手 URL + 逐條溯源（agent-report-health）                 | WebSearch 綜合標籤當來源                    |
| 反方／falsify 配額                                         | 只確認不推翻                                |

### 4.2 編輯室可退回研究的觸發

結構主編或事實席若發現：

- 論點關鍵支撐 **0 一手** 或 **單源**
- 時間線／金額／引語無法 Ctrl-F
- 「現場／口述」無公開足跡且未標 single-source hedge

→ verdict **block**，指令是「回 Stage 1 補研」不是「寫手腦補」。

這對齊睨說的：沒數位足跡很難寫；要嘛補一手，要嘛寫作時明確餵原件，要嘛砍該 beat。

## 5. 編排與成本（避免編輯室本身變成劇場）

| 模式            | 何時                                     | 投影室        | 正文室         |
| --------------- | ---------------------------------------- | ------------- | -------------- |
| **Full 編輯室** | depth EVOLVE / Fresh / A 級 / callout 後 | 3–4 席平行    | 包 A + 包 B    |
| **Thin**        | standard / 短修                          | 結構主編 1 席 | 僅 3.6（現狀） |
| **Micro**       | typo / 1–3 檔                            | skip          | skip           |

**成本護欄**：

1. 投影室 **≤ 2 輪**；第 2 輪只重跑「曾 block 的席」
2. 正文包 A 與包 B **可同 round 平行**（不同 agent）
3. 主編裁決表必須 **≤ 7 條必改**（防 critique 膨脹）
4. subagent claim 仍是線索（#31）：主編對 block 級 claim 抽 1 條重驗

**Context 隔離 checklist（每席 prompt 硬寫）**：

```text
你是 {角色}。你沒有寫過這份藍圖／正文。
只讀附件 A/B/C。不准讀 knowledge/ 舊文（除非 brief 明示對照 EVOLVE）。
輸出嚴格用編輯室報告模板。
不准重寫全文；只准列必改與理由。
```

## 6. 建議插入 REWRITE 的精確位置

```text
Stage 1 研究合成
    ↓
Step 2.0 投影藍圖（orchestrator 寫）
    ↓
⭐ Step 2.0-R 投影編輯室（NEW — hard depth）
    ↓  pass / 回修藍圖
Step 2.1–2.x 派 fresh writer
    ↓
Stage 2.5 覆蓋前
    ↓
⭐ Step 2.5-R 正文結構編輯室（NEW — 包 A）
Step 3.6 成品總驗（既有 — 包 B，可改名「正文事實編輯室」）
    ↓
主編合併 → ship
```

**命名建議（canonical）**：

- 方法論：`docs/editorial/EDITORIAL-ROOM.md`（薄，角色 + 模板 + 與 PROJECTION／3.6 邊界）
- 流程：REWRITE Step `2.0-R` / `2.5-R` 各一段 + 編排表加兩列
- 產物目錄：`reports/editorial-room/`
- Prompt：`docs/pipelines/EDITORIAL-ROOM-PROMPTS.md`（每席 copy-paste，禁即興）

不建議另開完整平行 pipeline 檔（避免 SPORE 拆檔前的膨脹）；先住 REWRITE + 一份 editorial canonical。

| 機制                     | 層級         | 編輯室怎麼接                     |
| ------------------------ | ------------ | -------------------------------- |
| research 反方 agent      | 材料         | 編輯室可引用「反方缺口」要求補研 |
| persona gap-audit        | 讀者缺口     | 可選併入讀者席，不取代結構主編   |
| Stage 3.5 / 3.6 verifier | 事實 atom    | **正文編輯室包 B**               |
| FACTCHECK-PIPELINE       | 事後／高流量 | 仍獨立；編輯室不取代             |
| 投影 5 題 gate           | 作者自檢     | 保留；編輯室是 **外部尺**（#69） |

## 8. Dogfood 與驗收

**第一輪 dogfood 候選**（擇一）：

1. 下一篇 depth EVOLVE（綠地）
2. 回放 Shopping Design 投影藍圖（已知面向巡禮 → 結構主編應 block）
3. 回放施振榮 v1 spine（炎上席應 block）

**驗收指標（質性）**：

- 投影室至少一次抓到「論點是摘要」或「可 shuffle」且 orchestrator 自檢沒抓到
- 正文室至少一次抓到「藍圖有全局功能、正文寫成導覽」
- 假陽性：立體群像被誤判成要矛盾驅動 → 炎上席／主編用 #77 擋下

**儀器化（第二波，勿第一天做）**：

- `editorial-room-health.py`：報告有各席 section、verdict enum、必改 ≤7
- 不自動判「結構對不對」（語意層留給 agent）

## 9. 分階段落地

| Phase           | 做什麼                                                                  | 產出                                     |
| --------------- | ----------------------------------------------------------------------- | ---------------------------------------- |
| **P0 設計鎖定** | 本檔 review；哲宇拍板 Full/Thin 觸發、席位最小集                        | 本 report + 決策                         |
| **P1 MVP**      | 只上 **投影編輯室**（結構 + 減法 + 炎上 3 席 + 主編）                   | PROMPTS + Step 2.0-R 一段 + 1 次 dogfood |
| **P2**          | 正文包 A（結構 + 論點兌現）與 3.6 並列命名為編輯室                      | Step 2.5-R                               |
| **P3**          | EDITORIAL-ROOM.md canonical；CLAUDE Bias 3 寫文章必讀；可選 UI 思考泡泡 | 物種層                                   |

**建議 MVP 最小席**：結構主編 + 炎上／倫理 + 主編裁決（3 個 context）。減法可併入結構主編第一版，降成本。

## 10. 待哲宇拍板（決策點）

1. **投影編輯室是否 depth 強制**，還是 opt-in 一週 dogfood 後再 hard？
2. **正文包 A** 是否與 3.6 同 round 強制，還是先只做投影室？
3. 主編席是否**永遠**主 session（推薦是），還是也可派 agent（不推薦：裁決權漂）？
4. 與睨產品（滑動留言）是否要 **reader 端展示**編輯室報告（公開透明度）還是 **僅產線內部**？

## 11. pen 一句（給下一個實作 session）
