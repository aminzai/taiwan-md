# Rewrite 引導工具研究計畫

日期：2026-09-07。讀者與決策者：哲宇。目標：找出近期成品失去可讀性與說服力的具體機制，並把 REWRITE 進化為 agent 可逐步取得任務、提交材料、收到編輯回饋與修訂的工具。研究與工程在同一工作樹進行。

## 範圍與假設

核心樣本為觀察者指定的 EZ WAY、黃崇仁、苯駢芘、演算藝術，以及早期黃魚鴞、張懸與安溥。前四為不滿意案例、後二為偏好參照；這是用途明確的目的性抽樣，不能推估全站品質退步比例，也不把早期文章當成事實正確答案。無相同題目、模型、來源與提示的控制實驗前，不把差異歸因於模型或單檔／多檔。

來源依序為文章正文與 Git 版本、研究與編輯席原始紀錄、相關官方來源，以及 agent 工具與評估的一手研究。所有架構選擇要回答它修正哪個已觀察失敗；機械合規與讀者品質分開驗收。

## 執行狀態

1. **進行中：對照研究與反證。** 完整冷讀六篇，追當時流程、研究和編輯判斷；核對最重要的因果鏈。研究分為文章成品比較與流程歷史兩條獨立唯讀分工，主代理負責關鍵證據重讀及綜合。
2. 待辦：至少兩個架構方案比較，先提交設計報告，明確定義現有 newsroom 與新工具的資料邊界。
3. 待辦：實作互動式 agent 協議、任務回饋、狀態保存、修訂與可追溯證據。
4. 待辦：真實案例試跑、負向協議測試、盲讀對照；紀錄尚需人類判斷的品質問題。
5. 待辦：完整報告、使用文件與本階段收官。

## 證據缺口

| 問題                     | 目前證據                                       | 尚缺／下一步                                             |
| ------------------------ | ---------------------------------------------- | -------------------------------------------------------- |
| 遵守流程是否保證成品品質 | 歷史日記與審稿已有「全綠仍遭讀者指出問題」案例 | 逐項對讀文章及審稿原文，避免只引用自我診斷               |
| 是否是多檔造成退化       | 只有使用者時間與品質對照                       | 追版本與實際執行，保留題材、來源、篇幅等替代解釋         |
| 新工具如何真正引導       | 現有 CLI 為薄路由、newsroom 已有事件及工件     | 盤點接點，避免另造互相矛盾的發布狀態                     |
| 品質如何驗收             | 六篇可用於失敗回放                             | 新案例需保留原稿、修訂稿及盲讀判斷，不能以通關數宣稱更好 |
