# seo-meta 多語言門檻校準的第一份實測底線

## 為什麼是今天做這件事

Issue #1264 由 stantheman0128 在 7/26 提出：`article-health.py` 的 `seo-meta` check 只對 `zh-TW` 註冊，`knowledge/en|ja|ko|es|fr/` 全被 `_is_excluded_path()` 排除，所以非中文版本的 title 與 description 長度沒有任何機器把關。他同時指出不能照搬中文的算法，因為現行門檻數的是 CJK 字元，套到拉丁字母會讓門檻恆為 0。

維護端 7/27 與 7/29 各回覆一次，兩次都說要排一個獨立 session 校準各語言門檻再改 registry。到今天為止，這個承諾沒有寫進 OBSERVER-QUEUE、沒有寫進 roadmap、也沒有寫進任何 inbox，只活在 issue 留言跟 memory 的 handoff 行裡。這正是 §神經迴路那條「memory 是自律，canonical 才是閘門」的形狀。

今天的 maintainer cycle 沒有 PR 可收、五個 open issue 也都不需要新回覆，所以把那個獨立 session 真正缺的東西補上：實測資料。門檻要用真實產出 dogfood 校準，不是憑想像設（REFLEXES #66）。本報告不訂任何數字，只把地面量出來。

## 量法與它的邊界

掃 `knowledge/` 全部 12 個語言目錄的 frontmatter，取 `title` 與 `description` 的**原始字元數**（Python `len()`），排除 `_` 前綴檔與 `all/` 中繼目錄。

這個量法的適用範圍必須先講清楚，否則下游會拿它當它不是的東西用：

- **拉丁文字語言（en / es / fr / pt / id / vi）**：字元數跟 Google 的截斷慣例（title 約 60、description 約 155-160）可以直接對照，數字有判讀力。
- **ja / ko / ar / ru / hi**：SERP 截斷實際是像素寬度而非字元數，各文字系統的字元寬度不同。這幾欄請讀成「相對於中文源頭膨脹了多少」的指標，不要讀成「超標幾篇」。
- **zh-TW 那一列跟現行閘門不可直接比較**：現行 `seo_meta.py` 數的是 CJK 字元（`TITLE_MAX_CJK = 45`、`DESC_MAX_CJK = 180`，canonical 120-160 容忍至 180），本表數的是全部字元，含數字、英文專名、標點。所以本表的 zh-TW「超過 160」不等於現行閘門會擋。

## 這揭露的事：不是補一個數字就能開的閘門

把上面兩張表放在一起讀，會得到一個跟 issue #1264 原本設想不同的結論。

原本的設想是：現行閘門排除了非中文版本，所以補一組以總字元數為準的門檻、註冊進 registry，缺口就補上了。實測顯示這條路走不通，因為**任何貼近 Google 慣例的拉丁門檻，都會在啟用當天標記掉八成以上的非中文 corpus**。en 有 713 篇、es 774 篇、fr 762 篇。這道閘門從來沒開過，今天是這批譯文第一次被量。

更關鍵的是第二張表。既然合格的中文 description 忠實翻譯後就是 3.8 倍長，那麼要讓譯文落進 160 字元，做的事是**替每個語言另外寫一段更短的 description**，把既有翻譯修短到不了那個長度。這會動到翻譯產線對 description 這個欄位的定義（它到底是譯文，還是各語言各自的產物），而不只是 `article-health.py` 的一個常數。

所以這件事的形狀是：一個 quality gate 數值調整，帶著一個跨 11 個語言、影響上萬篇譯文的後果，而且有兩條方向不同的路。這正是 BECOME §Step 0 把「threshold / quality gate 數值調整」列為 high-stake 強制升 Full mode 的理由，也超出日常維護 cycle 該自己拍板的範圍。今天的 cycle 到此為止，把它送進 OBSERVER-QUEUE。

## 三條路與它們的代價

供決策用，本報告不推薦執行任何一條。

**A. 拉丁門檻訂在實測現況附近（例如 description 400、title 120），只擋離群值。**
啟用當天警報量可控（各語言剩約一成），閘門立刻能上線防止新的極端值（1467 字元那種）。代價是這個門檻不對齊 Google 截斷點，等於承認 SERP 會被截，閘門守的是「別太離譜」而不是「SEO 有效」。

**B. 拉丁門檻訂在 Google 慣例（description 160、title 60），先以 warn 級上線不擋 CI。**
門檻誠實反映目標，但會產出八成命中率的警報。八成命中率的警報等同沒有警報，讀的人會學會忽略它，而且它會壓在每一次 article-health 輸出上。要讓它有意義，必須配一個實際的重寫計畫。

**C. 承認 description 不該是譯文，改成各語言獨立撰寫。**
方向上最對，跟主權的巴別塔的邏輯一致（每個語言有自己的第一人稱聲音，不是中文的投影）。代價最大：動翻譯產線的欄位契約，且上萬篇既有譯文的 description 要重生成。

三條路都不是今天能決定的。共同的前置是這份實測資料，現在它在了。

## 順帶對齊一件事

Issue #1264 body 最後提到 `ARTICLE-INBOX` 裡「台灣 BIM 與營建科技 英文版 metadata」那條寫中文版 description 189 字「亦略超標」，而檢查器判它 pass。這個落差的來源已確認：INBOX 那條數的是全部字元，檢查器數的是 CJK 字元，扣掉 `REVIT_MCP_study`、`GitHub`、`BIM`、`3D` 這些非 CJK 之後落在門檻內。兩邊都沒錯，是同一份規格用了兩把尺。若走上面任何一條路，順手把「字元數的定義」寫進 canonical，這類落差才不會再長出來。

## 本報告不做的事

- 沒有訂任何門檻數字
- 沒有改 `seo_meta.py` 的 registry 或 `_is_excluded_path()`
- 沒有改任何一篇文章的 frontmatter
- 沒有在 issue #1264 留言（對外回覆屬 §自主權邊界 human-only）

量測腳本是一次性的，沒有落進 `scripts/`。如果決策走 B 或 C，它應該長成常設儀器再進 repo，而不是現在先塞一支沒人會再跑的檔案。
