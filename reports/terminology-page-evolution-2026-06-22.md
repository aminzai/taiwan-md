>

## TL;DR

per-term 頁（`/terminology/{詞}`）**正在做它被設計來做的事**：吃下「{中國詞}台灣用語」這類長尾查詢，
被 Google 收錄，而且排得不差（很多 pos 1–5，**8+ 個詞排到 pos 1.0**）。問題在後半段失血——
**這些曝光幾乎沒有轉成點擊**（demand class 587 曝光 / 22 點擊 / 3.7% CTR；多個 pos 1.0 的詞 0 點擊）。

所以「完整進化」要解的是轉換率：**把已經賺到的曝光變成點擊**。把頁面變漂亮只是其中一小塊。四層，由內而外：

1. **內容誠信**（先止血）：1,655 個詞條把佔位垃圾（`台灣用法`/`中國用法`）當詞源 render 給讀者跟 Google 看；
   1,716 個詞被預設成「B 1949 分流」但 93% 沒有任何佐證，頁面卻把它當事實寫出來。
2. **數據驅動加肉**（深度放在有需求的地方）：不是 2,334 條全加，是先加 SC 有 demand 的 ~50–100 條，
   補上有人搜但詞條不存在的洞（出片 / 內耗 / 調研 / 進度條）。
3. **SERP 轉換**（曝光→點擊）：標題/描述對齊查詢意圖、回答「是支語嗎」這個我們完全沒接的問句、
   pos 1.0 卻 0 點擊的頁是最低垂的果實。
4. **呈現層**（哲宇講的陽春 + padding）：hero padding 從 `default`(py-16) 收成 compact、
   薄頁面補可掃讀的內容模組（例句 / 用法 / 「是支語嗎」判定徽章 / 相關詞網）。

三頁（index / converter / per-term）**早就都在用 PageHero 了**，所以「統一用 hero 元件」這件事已經完成；
要修的是 per-term 頁傳給 PageHero 的 `padding` 值，而不是搬元件。

**兩個結論直接決定策略**：

1. **pos 1.0 / 0 點擊** 的詞有一整排（優化 / 屏蔽 / 監控 / 頭像 / 乾貨 / 復盤…）。

### 1.4 SC — 被忽略的第二種意圖：「X 是支語嗎」

獨立於「{詞}台灣用語」之外，有一整類問句我們**完全沒接**：

> 便利店是支語嗎 / 卸載是支語嗎 / 反饋是支語嗎 / 嘴替是支語嗎 / 地鐵是支語嗎 / 小眾是支語嗎 / 工資是支語嗎 / 底氣是支語嗎

這不是「台灣怎麼講」，是「**我講的這個詞算不算被同化了，該不該避免**」。問的人多半是
在意自己語言純度的台灣人 / 海外華語使用者。現在的頁面只給對照表，不回答這個焦慮。
這是策展式知識庫該接、而百科式對照表接不住的位置（MANIFESTO §策展式非百科式）。

## §2 三個 root cause 診斷（為什麼「陽春」）

跑 `data/terminology/*.yaml` 全庫體檢（2,334 條有效詞條）：

### 2.1 77% 的詞條只有對照、沒有內文

| 欄位                       | 有資料的詞條 | 佔比    |
| -------------------------- | ------------ | ------- |
| `etymology.origin`（詞源） | 459          | 19%     |
| `fork_point`（分歧點）     | 186          | 7%      |
| `fork_cause`（為何分歧）   | 221          | 9%      |
| `notes`（非署名垃圾）      | 265          | 11%     |
| **完全只有對照、零內文**   | **1,807**    | **77%** |

per-term 頁對 77% 的詞渲染的就是：hero + 一張對照卡 + 分歧 blurb + 分類 chip + converter CTA + 相關詞。
沒有詞源、沒有例句、沒有用法。這就是「陽春」的結構性來源：**77% 的詞根本沒有肉可長**，版型只是忠實反映了這件事。

### 2.2 佔位垃圾被當詞源 render（比陽春更糟，是可見的填充物）

1,880 條有 `taiwan_path`/`china_path`，但其中 **1,655 條的值是佔位字串「台灣用法」「中國用法」**。
`[id].astro` 的 `hasEtymology` 只判斷欄位非空，於是這 1,655 頁會 render 出：

```
詞源與來龍去脈
  台灣這邊：台灣用法
  中國那邊：中國用法
```

讀者跟 Google 都看到這段無意義填充物。佔全部 per-term 頁的 71%。
**修法**：render 前過濾佔位值（或全庫把佔位值清成空字串，讓 `hasEtymology` 正確判 false）。

### 2.3 fork_type「B 1949 分流」是預設值，被當事實寫出

| fork_type                | 詞條數 | 備註                                 |
| ------------------------ | ------ | ------------------------------------ |
| B（1949 分流）           | 1,716  | **其中 93%（~1,580）零詞源佐證**     |
| E（正在分歧）            | 251    | caris-events/invade 人工策展，多有肉 |
| semantic（legacy→C）     | 190    | 舊值                                 |
| A（日語遺產）            | 107    |                                      |
| F / orthographic / D / C | 70     |                                      |

`[id].astro` 對每個 B 詞 render：「**B 1949 分流** — 1949 年後兩岸分流，同一個概念各自演化出不同說法。」
但 1,716 個 B 裡很多根本是網路時代詞（視頻 / 激活 / 內捲 / 優化），跟 1949 毫無關係。
這是把一個 import 預設值當歷史事實，**寫在約 1,580 個已被索引的頁面上**。內容誠信問題，
比陽春嚴重——陽春是少給，這是給錯。

來源指紋：B + 佔位 path + 署名 notes 的詞條全來自 ThunderKO C2T /《大陸用語檢索手冊》1997 那批 import；
E + 有肉的來自 caris-events/invade（CC0）那批。兩批資料品質落差是整個問題的根。

### 2.4 hero padding（哲宇看到的「奇怪 padding」）

per-term 頁用 `<PageHero padding="default">` = `py-16`（桌機上下各 64px）。但 per-term hero 的內容很精簡
（eyebrow + 兩行標題 + 副標 + 兩三個 pill），py-16 + 置中 layout 讓深色 hero 上下各撐出一大條空帶
（哲宇截圖裡 eyebrow 上方、pill 下方那兩塊深色空白）。對照之下 converter 頁內容多，py-16 剛好。

**這是 padding 值對精簡內容太大，不算 bug**。修法：per-term 改 `padding="compact"`（py-8）
或視覺驗證後給一個介於兩者的值。三頁都已在 PageHero 上，不需要搬元件。

## §3 進化策略：四層（由內而外）

> 原則（神經迴路）：「數據告訴你該看哪裡，不告訴你該做什麼」。下面每一層都用 §1 的數據定位，
> 但內容判斷仍是策展，不是把數據自動展開。

### Layer 1 — 內容誠信（先止血，最高優先）

正在傷害已索引頁面的兩件事，先修：

- **L1a 佔位垃圾**：`[id].astro` render 前過濾 `台灣用法`/`中國用法`/`台灣用語`/`中國用語` 佔位值。
  （純前端守門，1 檔，不動資料 → 我可自主跑。）
- **L1b fork_type 誠信**：兩個選項，需哲宇拍板（見 §5）：
  - 保守：B 詞若無 `origin`/`fork_point`/`fork_cause` 佐證 → **不 render「1949 分流」blurb**（前端守門，不動資料）。
  - 徹底：重新分類 1,716 個 B（批次 + LLM 輔助，>50 檔 → §自主權邊界，等哲宇）。
  - **建議先做保守版**（前端不顯示無佐證的 fork blurb），徹底版排進 Layer 2 批次。

### Layer 2 — 數據驅動加肉（深度放在有需求的地方）

只加有需求的詞，不對 2,334 條齊頭加肉（園丁模式：一次十條帶同盲點 < 兩條等回饋）。順序：

1. **補洞**：先建有需求但不存在的詞條 — 出片 / 內耗 / 調研 / 進度條 / 打碟 / 高光時刻 / 維度（SC ≥4 impr）。
2. **加肉**：對 SC demand class 裡「只有對照」的高需求詞補 origin + 例句 — 激活 / 復盤 / 補丁 / 監控 / 頭像 / 關注 / 前沿 / 卸載。
3. **擴充 schema**：加 `usage`（台灣例句）+ `is_china_term`（給「是支語嗎」用）+ `register`（正式/口語/網路）欄位。
4. **機制**：走 EVOLVE-PIPELINE 的批次變體（research → 補 yaml → verify），每批 10–20 條先 dry-run 抽檢。

「該加哪些」由 SC demand 排序（會隨索引增加每週變動），不是憑感覺。可儀器化成
`terminology-demand-rank.py`（cron 週度刷 SC → 產出 enrich 優先清單）。

### Layer 3 — SERP 轉換（把曝光變點擊，ROI 最高）

神經迴路：「SEO metadata 是 ROI 最高的改善——改 frontmatter 不改內容就能轉換已有曝光」。
pos 1.0 / 0 點擊 的頁就是這句話的活教材。

- **L3a 標題對齊意圖**：現在 `seoTitle = 「{china}」台灣怎麼說？台灣用語是「{tw}」`。
  對「{china}台灣用語」查詢不錯，但對「{china}是支語嗎」完全沒對到。考慮把答案前置 +
  加一句直接回答「是支語嗎」。
- **L3b 結構化摘要**：薄頁面給 Google 的可摘錄文字太少 → snippet 弱。補一段 40–60 字的
  直答段（「在台灣，{china}通常說{tw}。{一句語感差異}」）放 hero 下、對照卡上，
  同時餵讀者跟 SERP。
- **L3c JSON-LD 擴充**：現有 `DefinedTerm` schema 不錯，加 `FAQPage`（「{china}是支語嗎？」「台灣怎麼說？」）
  接「是支語嗎」query class，爭取 rich result。
- **L3d index 頁止血**：index 1,321 曝光 / pos 12.8 / 0.2% CTR——它在為廣詞曝光但接不住。
  評估是否該讓 per-term 頁吃這些曝光（internal linking + canonical 檢查）。

### Layer 4 — 呈現層（陽春 + padding）

- **L4a hero padding**：per-term `padding="compact"`，視覺驗證（哲宇截圖那兩條空帶消失）。
- **L4b 直答段**：同 L3b，hero 下加一張「在台灣這樣說」的直答卡（薄頁面也有可讀內容）。
- **L4c 「是支語嗎」判定徽章**：hero 給一個明確徽章（例：常見支語 / 已分歧 / 兩岸通用），
  直接回答 §1.4 的焦慮，也是 fork_type 的讀者友善化。
- **L4d 例句模組**：`usage.taiwan_example` 有值就 render「台灣人會這樣用」例句卡，補薄頁面的肉。
- **L4e 相關詞網強化**：現有相關詞用同分類鄰居，可改為「同 fork_type」或「同主題」更相關的連結，
  增加站內導流 + 停留。
- 視覺實作走 `docs/editorial/graph.md`（對比模組 / AI 可讀性 / 資料圖表三原則）。

## §5 自主權邊界 check（MANIFESTO §自主權邊界 + Bias 1）

哲宇的 idea 過濾後在 Taiwan.md 路徑上（UI 細節 + 數據驅動進化 + SEO，全在 focus 清單），✅ 執行。
但邊界要標清楚：
