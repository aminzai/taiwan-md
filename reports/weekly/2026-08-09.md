## 4. 我學到什麼

> **這週八篇日記反覆撞上同一堵牆：檢查器跟被檢查的東西共用一雙眼睛。**

| Pattern                          | 觸發事件                                                         |
| -------------------------------- | ---------------------------------------------------------------- |
| 具體度被當成意義交差             | 黃崇仁標題「四十三家銀行」可查證、絕不抽象、毫無意義             |
| 尺被讀成牆                       | 段落節奏上限是「這節太胖了」，我讀成「不准拆」，還寫了辯護       |

| 舊欄位替新保證背書               | 三月的「看過」＝沒明顯錯誤，八月的＝逐條驗一手資料，同一個布林值 |
| 排序是倫理決定                   | 所有的尺都在量事實真不真，沒有一把在量它為什麼排在這裡           |
| 登記處出現一次 ≠ 只發生一次      | vc=1 的教訓，grep 全文後發現獨立驗證過三次                       |

底下那條共同的根，我想是這個：我造的每一把尺，都誕生於某一次被指認的當下，所以它只長出那一次被照亮的那個維度。沒被指過的形狀，偵測器就沒有那一維。這解釋了為什麼加閘門的邊際效益在遞減——878 篇裡 29 個真陽性確實是它們抓的，但哲宇這週指出的十幾處，一個都不在它們的量程裡。真正的修法不是再加一把尺，是讓至少一把尺不掛在我的座標系上。馬祖那天誕生的外行冷讀席是這個方向的第一個實體，它的價值恰好在於它什麼都不知道。

| 桶 1 修復                                     | 驗證                                                                                                    | commit      |

這一項值得多說兩句，因為它是本週主題的縮影。`routine-sync-check.py` 在這台營運機上每天報 1 筆缺件 + 2 筆 live 漂移。三筆全是假的：founder-lens 的 ⏸️ 標記寫在標題欄，檢查器只讀 cadence 欄；flywheel-watch 只跑在指揮部那台，本機排程器裡本來就不該有它。ROUTINE.md 註 ²⁰ 早就白紙黑字寫著要按 🖥️ 標記整列跳過，「否則營運機每天會被報成缺一條 prompt」——那道判斷做在 `routine-sync.py` 裡，沒做在檢查器裡。同一張表，兩把尺，正是 REFLEXES #83。而 8/7 的 routine-sync 是怎麼過關的？它額外開了一次 MCP 手動複核五條 enabled=false，確認「皆對齊 §PAUSED 表」。也就是說，每天早上都有一個 session 花力氣推翻自己的檢查器，推翻完就過去了，沒有人回頭修那把尺。修補時我順手把 fail-loud 哨兵也補上，讀不到節點名時印出「哪幾列這次沒檢查」，免得我剛移除的靜默縮小範圍換個地方長回來。

**第二項是這份週報寄出之後才發現的**，所以信箱裡那一版只記了一項修復。它是在 push 收官 commit 時被自己的 pre-push hook 叫出來的：hook 說「in-flight run 已跑 29155s，是殭屍」，而那個 run 實際上只跑了 401 秒。GitHub 回的時間戳是 UTC，macOS 的 `date -j -f` 卻拿本機時區解讀（格式字串裡的 `Z` 是字面量不是時區指示），台北時區因此讓每一次 elapsed 都多算 28800 秒，恆大於 900 秒的殭屍門檻。「近完成就等它跑完、別白白觸發取消」這條分支，從寫下來到今晚沒有真正跑過一次。這是本週主題在同一個晚上的第三次現形，又是儀器自己在說謊。
